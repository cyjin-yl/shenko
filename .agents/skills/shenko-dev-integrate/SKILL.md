# 整合并继续交付

先读 [shenko-dev 根哲学](../shenko-dev/SKILL.md)；已读且未变化时复用理解。
自主选择分支与整合方法，不增设逐提交、逐 PR 或逐依赖的人类批准流程。

## 目标

让已经完成的成果进入可继续开发、运行和评审的真实 Git 状态。

## 处理实际整合

- 先确认当前分支、未提交改动、目标仓库和真实权限，保留其他人的工作。
- 可以 merge、rebase、cherry-pick 或采用合适的组合；按实际历史和协作选择。
- 解决冲突时理解两侧意图，不机械接受一边或用覆盖文件消除报错。
- 相关并行成果整合后只检查会受组合影响的行为，复用仍有效的证据。
- 按真实权限提交、推送并更新 PR；记录真实作者、失败和当前状态。
- 多行 PR 内容用结构化参数或正文文件，保持准确换行和可复查描述。

## 权限与外部等待

实际 GitHub 权限决定能做到什么，不能靠写文档制造权限。
不修改 branch protection 来绕过阻塞，不伪造批准或测试成功。
若 review、合并权或外部系统暂不可用，保留具体状态并继续其他可推进工作。
修复已有 CI 或 review 中的实质问题；不要把等待某个 PR 当作整个开发停止条件。
当前任务明确限制推送或文件范围时遵守该范围，准备好可接续的整合结果。

## 足够的结果

指出整合后的 commit、分支或 PR，以及真实剩余阻塞即可，不要求额外仪式。
按 [适量验证](../shenko-dev-verify/SKILL.md) 处理具体组合风险，勿重跑无关证据。
局部交付成功后继续用户完整目标，除非当前委托已经明确完成。
