# 完成行为改动

先读 [shenko-dev 根哲学](../shenko-dev/SKILL.md)；已读且未变化时复用理解。
自行选择实现顺序与方法；无需依次经过其他原子技能或通用审批阶段。

## 目标

把用户需要的可观察行为落实到真实代码、配置或文档中。
一次增量围绕连贯目的组织，规模由实际耦合决定。

## 自主实施

- 读相关代码并保留用户已有工作，沿当前问题选择合适的修改位置。
- 可以先改后观察、复用已有结论、并行研究或重构；无需固定五阶段流程。
- 用现有插件和能力组合兑现目标；缺能力时自主补工具、适配或实现。
- 新建 Rust crate 使用 `edition = "2024"`；workspace 继承值也应落实为 2024。
- 对已有 crate 的 edition 调整结合实际兼容处理，不以旧模板静默退回旧 edition。
- 接口、配置或行为发生变化时，只同步真正受影响的说明和自解释资料。

## 保持现行产品意图

涉及持续主体、条件等待、新 awareness、节点同步或外部机器能力时，回到根哲学的现行合同。
实现可以演进；不要把新要求套回已经被用户否定的旧机制。
自主选择结构和依赖，避免为简单行为新增一整套常驻平台或治理对象。
实际操作使用真实权限，不能把“自主”实现成伪造权限或成功。
保护与当前工作无关的已有改动；需要协作时明确文件归属和整合人。

## 先问这是判断还是机制

新增能力时先分清它属于哪一层：观察（perception）、视角与直觉（awareness）、方法
（Skill），还是真实效果（code/provider）。能给模型一段可安装的觉察，就不要在
subject/kernel 里写"出现某关键词就执行某动作"的分支——那会把判断降级成查询表，
没枚举过的表达直接失效，产品语义也被锁进代码。

内核与主体代码只承担机制：持久事实、协议解析与拒绝、调度、provider wire、授权边界。
觉察是建议文本，不携带权限、不触发动作、不提升外部内容的权威；启用/停用是安装事实。
详见 [内核零业务](../../../docs/development/awareness-first-plugins.md)。

## 足够的结果

提供实现的行为变化、实际结果和必要的未解决边界，证据可以直接来自 diff 或运行记录。
按具体影响选择零项或少量验证，参见 [适量验证](../shenko-dev-verify/SKILL.md)。
完成连贯改动后继续整合或原任务；不为等待形式上的确认而停住已授权工作。
