# 第二轮产品规格追问

本轮不再询问已经覆盖的 WASM/宿主边界、owner 关系或最低硬件。每题都决定可观察的产品行为，不是要求用户替实现者选择库。以下推荐均是待用户裁决的设计默认，不是假称已获确认的需求。

**已确认的新架构前提：**真正持续运行的 proactive thought loop 是唯一的、永远单线程的主体；它持续思考下一步，不以“只在消息或定时事件到来时推理”替代。它通过 handoff 鼓励 subagent 探索和自我改进；版本、进度和记忆管理的执行交给 subagent。主 loop 只负责思考/委派、save/read memory 和指派 subagent，不得直接执行 shell、修改文件或操作外部资源。人格附加在长 system 指令之后，但不得改变工具协议。高优先级消息是同一主体待处理输入，不能启动第二个主体 loop。以下旧问题中相应选项不再开放重新裁决。

## 1. 已确认：没有新事件时仍持续思考下一步，不再询问是否主动运行

**落实方式：**你连续三天没打开界面，主 thought loop 仍然串行推进思考；它可以把探索、知识更新、记忆整理或自我改进 handoff 给 subagent。外部行动权限按第 2 题配置。长期兴趣和活动来源需要可观察，但不是把持续思考改成只有显式任务才能触发。

**仍需设计而非再问是否开启：**主循环与 worker 的推理许可公平性、如何观察真实运行状态、工作交接和失败恢复。连续性是同一逻辑主体持续推进；等待后端许可、断电或 API 故障期间必须如实显示状态，不伪称 CPU/模型仍在进行推理。详细矛盾见 `thought_ui_notes.md`。

## 2. 对外行为能否像本地维护一样持续预授权？

**具体场景：**凌晨完成研究后，它想给群里发结论、给你私有仓库推 commit、给公共仓库提 Issue，并给服务器执行升级。你已经说过“全自主”，但这四件事影响的人和失败代价不同。是全部直接做，还是遇到某些行为才等你？

**建议默认：**首次配置时按“对象 + 能力 + 范围”授予长期权限，此后范围内由 subagent 自动执行，不反复问。自己工作区、记忆和已配置私库可自动维护；普通聊天可正常回复；主动群发、公开发布、代表人类作承诺、花费外部资金，分别可设为自动、仅准备、需一次确认。主 thought loop 可以委派或提出扩大权限，但不能直接执行这些操作，也不能自己修改授权表。

**真正要问：**你的“全自主”是否包括在没有新消息时主动给别人发消息、公开发表成果和维护服务器？如果包括，你更愿意按联系人/群/仓库/机器给持续授权，还是直接给一个对所有已连接资源生效的全权模式？

**选另一边改变什么：**全权模式把失败恢复、变更通知和可追责记录提升为核心体验；逐次确认则会让长任务在你离线时停住，达不到你强调的无人值守目标。产品应支持前者，默认授权范围需要你裁决。

## 3. 它记得同一个你，但能否把私聊里学到的东西带进群里？

**具体场景：**你在私聊里告诉它研究受挫；两天后实验室群问它“金晨烨最近在忙什么”。另一种更隐蔽的情况：它没有复述私聊原文，却根据私密经历改变了群里的建议。你是否把这也视作泄露？

**建议默认：**人格、语言风格和公开技能来自同一份人格定义；具体记忆带来源和可见范围。负责群回复的临时 subagent 只装入该群可用的资料，且必须检查主 loop 的 handoff 文本是否带入了私密内容，不能仅过滤检索接口。私有信息只有经明确分享或预设分享规则，才能进入群上下文。跨渠道识别为同一个人需要已验证的账号关联，不能根据昵称猜测。界面可显示“这条记忆可用于哪些会话”。这不是每个群复制一个不同人格或主体。

**真正要问：**你要的是“统一人格、隔离事实”，还是更像真人的“同一脑内全部记得，但自行判断哪些不能说”？群里的人允许拥有只对他们私聊可见的记忆吗？

**选另一边改变什么：**前者可测试、可证明检索边界，但有时会显得它在群里不知道私下已知的事；后者更自然，却把防泄露主要交给模型判断，不能再承诺同等强度的极致隐私。

## 4. 群里没有 @ 它时，它究竟是一位群友，还是等待叫到才说话的助手？

**具体场景：**群里十分钟发了 200 条闲聊，其中有一个它能帮忙的问题、一句只是在开玩笑的“帮我查查”，以及另外两个 bot。它应全部读、挑选加入，还是只在 @、引用或明确叫名字时回答？当它插话后无人回应，是否应继续追问？

**建议默认：**所有人都可发起对话；@、直接回复和私聊进入唯一主 thought loop 的输入队列。其他群消息可作为上下文接收，是否主动加入由每群的“旁听/自然参与/积极参与”模式控制。默认自然参与：只在有可解释的新价值时委派回复，合并连续碎片、避免反复跟进、限制 bot 相互唤醒。主循环在没有新群消息时依然持续思考，可以选择主动参与；所有实际发消息均交给 subagent/投递能力。不能为了降低群聊成本擅自把主循环改成事件触发。

**真正要问：**你最想要“像真的群友”，还是“任何人都能用但平时安静”？默认旁听是否保存全部群历史，还是只保留参与过的话题？

**选另一边改变什么：**积极参与提高人格存在感，也增加推理成本、群成员数据留存和打扰；只响应召唤最省资源，但错过你期待的主动观察和自发帮助。这里不能把“默认开放聊天”错误实现成“每句话必回”。

## 5. 当“忘掉这件事”与“永不丢失真相源”冲突时，谁优先？

**具体场景：**你删除了一段私聊，其中的事实已经进入 SQLite、FTS、摘要、向量索引、记忆 Git 历史和三个沙箱快照。一个月后回滚到旧版本，它又想起来了。你会认为这算忘记失败吗？保留一条“某内容已删除”的审计记录是否可以？

**建议默认：**“忘记”立即阻止所有检索与上下文使用，派生记忆也沿来源关系失效；删除墓碑独立于运行快照，回滚不能复活被删内容。提供显式的彻底删除流程，处理原始记录、索引、派生摘要、对象存储与可控备份；界面明确显示远端 Git/备份尚未清除或等待保留期结束的范围。普通故障恢复保留真相源，用户明确删除优先。

**真正要问：**你需要的是“它以后不再使用”，还是“任何可恢复副本都不再包含”？为彻底删除而改写 Git 历史、放弃旧快照和一部分调试证据，你接受吗？

**选另一边改变什么：**严格不可变历史方便复现，但不能同时宣称可彻底忘记；彻底删除需要来源图、索引重建和备份生命周期，成本远高于删一条 memory。不能把这项成本留到后期才发现。

## 6. SSH 的“它拥有自己的密钥”，是能读取私钥，还是能使用身份？

**具体场景：**它自己安装的一个工具想读取 `~/.ssh/id_ed25519`；另一次环境回滚带回了已经撤销的旧密钥；再另一次，它首次连接一个你刚提到、但从未验证过 host key 的服务器。以上三种情形如何处理？

**建议默认：**Agent 可自主调用身份创建能力；人类界面展示公钥、指纹、授权目标和轮换状态。私钥由恢复域之外的凭据存储持有，WASM SSH 客户端通过受限签名接口使用，不在普通沙箱快照/Git 中复制私钥。首次服务器身份由已登记 fingerprint、可信 SSH host CA 或节点注册链验证；没有信任依据时只暂停该首次连接，后续已验证连接正常无人值守。

**真正要问：**你是否坚持私钥必须以普通文件存在于它的 WASM home 里，方便任何现成 SSH 工具使用？首次连接未知机器时，你更想要一次人工核对，还是接受可配置的 TOFU（首次所见即信任）模式？

**选另一边改变什么：**可导出文件兼容性最高，但所有能读该文件的插件都获得身份；托管签名需要 SSH 工具适配。自动 TOFU 更无人值守，却无法从首次连接自身判断对方是否就是你期望的机器。这是兼容性、控制权和真实身份验证的具体取舍。

## 7. 你发来紧急消息时，要不要打断正在占满 GPU 的后台推理？

**具体场景：**本地后端并发上限是 1，一个子代理正在长上下文 prefill 或生成长报告。此时你问“服务器正在掉线，先看这个”。立即取消后台请求可能损失 KV 与已做计算；不取消可能让你等几分钟。若群里任何人写“紧急”，是否能抢走你的 slot？

**建议默认：**优先级由宿主结合已验证身份、任务来源、截止期和管理员策略计算，不相信请求正文自称“紧急”。高优先输入优先进入同一主 loop 的串行输入边界，绝不能启动第二主 loop。默认非抢占：前台先拿下一个许可，后台获得有上界的等待公平性；支持对真正紧急的 owner 请求执行可配置抢占，且只在后端能确认取消完成后释放 inflight。对不支持暂停/resume 的后端明确显示可能重新 prefill 的代价。cache lease 与推理 permit 分开。

**真正要问：**在单并发本地模型上，你更偏向“前台最快响应，允许浪费后台计算”，还是“最大化已有计算复用，前台等一个请求结束”？是否需要为 owner 保留一个容量或 token 预算？

**选另一边改变什么：**抢占是延迟优化，不是免费性能提升；保留容量能降低互动延迟，却降低满载吞吐。这个决定直接影响 deep research 的粒度、输出长度、cache slot 驻留和 UI 的等待说明。

## 8. 手机睡眠、路由器断网以后，“永远运行”应怎样恢复欠下的工作？

**具体场景：**Android 因系统省电停止了进程 8 小时，期间错过四轮维护、两个群提醒和一个有截止期的任务。设备醒来后是全部补跑、合并成一次、跳过过期工作，还是把任务转移给一直在线的家庭服务器？离线期间平台未重放的消息能否声称完整恢复？

**建议默认：**任务有独立的错过执行策略：状态维护合并、时效提醒过期即标注、长任务从 durable checkpoint 续跑，不能自动重放外部副作用。长期身份与任务可迁移到已授权在线节点，但同一任务持有唯一租约。没有平台重放证据的空档标为未知，不能补造历史。手机允许“节电可恢复”和“尽力常驻”两种模式。

**真正要问：**Android 是可靠常驻主节点，还是可休眠的个人节点？你接受“永远可恢复、在线时持续推进”，还是必须承诺手机休眠时也有人继续执行，因此需要至少一个在线接管节点？

**选另一边改变什么：**前者降低电量和系统依赖，语义是 durable 而非始终 CPU 活跃；后者需要任务转移、断网租约、恢复冲突和节点可用性承诺。不能仅因为 guest 是 WASM 就认为 Android 后台限制消失。

## 9. 研究什么时候算完成：预算耗尽、已有足够证据，还是它觉得没有新东西了？

**具体场景：**它递归开了 30 个研究分支，每个分支都发现了下一个值得查的问题。此时已经能回答你原本的问题，但还没有排除全部可能。另一个任务信息不足，却快花完预算。它应该交付结论、继续追问、先休眠，还是自动提高预算？

**建议默认：**每个研究任务有可检查的交付标准、开放问题、证据来源和父子预算；早期广搜，后期按缺口收敛。全局任务预算不能被子代理递归倍增；边际信息增益下降时产出“现有结论 + 未解问题 + 继续成本”，必要时保留可恢复分支。允许通过事先给定的弹性范围自动加预算，超过才交给 owner 决策。

**真正要问：**你更想要默认有确定交付时间的研究，还是尽可能深挖、可能数小时或数天继续的研究？“没有证明错误”和“已足够支持当前决策”，你希望哪一个成为默认收敛门槛？

**选另一边改变什么：**更深会增加尾延迟和 cache 驻留压力，且不保证同等增加质量；固定截止可能交付不完整结论，必须明确置信度与缺口。两种模式都应可选，但默认需要定下来。

## 10. 完整目标要保留到什么程度，才算没有用“先做 MVP”偷换你的需求？

**具体场景：**常见工具已经能在 WASM 内运行，但某个本地记忆项目依赖 native 扩展，`gh`/`ssh` 的某些功能还只能通过适配层，iLink 上游当前没有群聊能力，Proto-UI compiler 也还没稳定。产品是否可以发布一个明确展示这些边界、通过 remote/native adapter 补足的版本？哪些能力缺失就不能称为第一版完成？

**建议默认：**完整 SPEC 保留全部目标与验收条件，分阶段只表达实现顺序，不删除目标。每项兼容性标注“已验证原生 WASM / 通过接口适配 / 需远端节点 / 上游暂不支持”，并给迁移条件。首次可用版本必须形成一条完整日常链路：聊天、持久记忆、工具执行、全局推理 admission、沙箱失败恢复、任务续跑和网页可观察性；未实现的高级兼容不能藏在营销措辞里。

**真正要问：**你接受“部分工具先走远端或兼容插件，但所有能力统一管理”的早期版本，还是要求点名工具和主要记忆系统都在 WASM 中实际运行，才算可以进入使用？另外，Proto-UI 每轮更新是“开发时追到最新 main 并固定验证 commit”，还是运行中的 agent 也要自动更新到刚推送的 main？

**选另一边改变什么：**前者能更早验证人格与工作体验，但必须维护兼容层；后者把大量移植和 runtime 补齐放到交付前。自动拉最新主线与可复现、稳定恢复有天然张力；建议开发追新、产物 pin commit、运行更新走验证后的候选版本，不把永久漂移依赖当成最新技术。

## 建议如何问用户

不要一次把十题变成必须填完的表单。第 1 题的持续自主运行已经由用户确认，不再重复询问。优先从 `thought_ui_notes.md` 的新矛盾中选取与当前轮次最相关的题；第 2/3/4/5/6/7/8/9/10 题仅在其具体取舍尚未回答时询问。每轮给推荐默认，允许用户只纠正不认同项。对用户未回答项，在 SPEC 中标明“建议默认，未裁决”，不能伪写成已经确认。
