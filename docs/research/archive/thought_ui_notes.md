# 单一持续 Thought Loop：产品语义、界面与新增规格矛盾

状态：根据用户新增架构进行的规格研究。不是实现方案已经获批，也不改变用户明确要求。

## 1. 已确认的核心语义

- 主体只有一个；主 thought loop 在逻辑上唯一、永远单线程，持续思考下一步。
- 不用 heartbeat、队列有任务才唤醒、周期性定时研究来替代这一持续循环。
- 主 loop 思考、read/save memory、产生指派和 handoff；不能直接 shell、读写任意文件、发网络操作或修改外部资源。
- 探索、研究、自我改进，以及版本、进度、记忆管理的具体执行，交给 subagent。
- 高优先消息送入这个主体的输入序列。优先级调度不意味着再建立一个 owner-chat 主体。
- “单线程”约束主逻辑链；subagent 可并行，但其所有模型请求仍共享同一个推理资源组的 admission。
- 人格是同一逻辑主体的一份版本化定义，追加在长 system 规范后；人格内容不能改写工具 schema、消息封套、ACL 或宿主状态机。

## 2. 用户界面的中心应是什么

### 2.1 主界面显示“一位正在生活与工作的 Agent”，而非一排平等的主 Agent

顶部只保留一个主体状态和统一人格头像。旁边展示真实状态：正在进行下一轮思考、等待推理许可、等待记忆读取、正在委派、推理服务暂不可达、恢复中。没有进入模型执行的等待不能标为“正在推理”；服务断线不能用永远旋转的“思考中”掩盖。

主体下方呈现当前关注的工作、已委派子任务和最近完成的结果。子代理用任务名和角色标识，默认不塑造成独立人物，也不各自拥有一份会长期漂移的人格。用户仍然与同一主体对话。

### 2.2 让布局说明工作状态

建议三层信息结构：

1. **当前关注**：一个连续的主体区域，显示公开意图摘要、当前收到的 steering 和下一项已声明行动。
2. **工作展开**：有真实子任务时展开任务分支；显示委派原因、运行/排队/阻塞、证据和结果。没有分支时不留下空框或假工作动画。
3. **结果与记忆**：成果、待决定事项、最近保存的记忆、恢复记录。技术细节如 KV slot、queue permit、snapshot hash 放在可展开的运行详情，不塞进普通群聊。

动画用于表示已发生的状态转移：委派卡片从主体区域进入工作区、结果回到主体活动流、暂停任务保持位置但改变状态。不要用随机漂浮、假 token 滚动、虚构不断增加的完成百分比来制造“活着”的感觉。

### 2.3 群聊只是同一主体的一个发言场景

每个渠道有已验证的 audience scope、消息序列、发送回执和会话状态，但不建立“QQ 人格”“飞书人格”“私人主人格”三个独立主体。临时对话 subagent 可以使用共同人格的固定版本与该场景允许的上下文，代表同一主体作答。

用户可以进入某条回复查看：由主体收到哪个事件、委派给哪个 worker、使用了哪些允许公开的来源、何时投递成功。普通群成员不必看到 worker 名称或内部任务编号。

## 3. 可观察性与内部思维不能混为一谈

**应展示的可核验事实：**

- 已声明的工作意图及简要理由，例如“先检查离线原因，资料研究继续排队”。
- 刚发生的 handoff：任务范围、目标、结果要求和经过权限过滤的输入来源。
- 当前工作状态：排队、执行、等待输入、失败、恢复、完成、投递不确定。
- 子代理报告与证据、实际工具调用、变更 diff、记忆保存的来源、任务预算消耗。
- 推理请求是否已开始、elapsed time、已知后端统计等真实遥测。

**不能默认伪造的东西：**

- 由 UI 或另一模型现编的“我现在脑内每个 token 正在想什么”。
- 根据 token 数反推出的心理情绪、百分比进度或已经做出的决策。
- 把执行器私有日志、秘密工具参数和跨群上下文原封不动显示在公开活动流。
- 把高层公开说明称作完整思维转录。应命名“当前意图”“行动说明”“工作记录”，明确它们是对外可解释记录。

如果后端实际返回可公开的 reasoning summary，可以单独呈现为“模型提供的推理摘要”，仍需按受众权限过滤。后端没有提供时，显示事实状态即可，不为视觉连续性编造思想。是否保留某个本地后端额外输出的调试字段属于管理员设置，不能假设所有 API 都具有这种字段或语义。

## 4. 人格尾置、工具协议与隐私隔离

### 4.1 尾置人格保持表达一致，不能作为工具协议的安全边界

建议 system 结构明确分成稳定协议/主 loop 职责、能力规则、任务语义、人格尾段。人格尾段影响语气、兴趣、互动风格，不增加工具权限。宿主执行工具 JSON schema 和 capability check；即使模型按照人格写了不合协议的输出，也必须报可恢复的校验错误，而不是解析成任意 shell。

长 system 的稳定前缀有利于缓存，但人格版本变化会使其后缀及后续上下文的缓存复用受到影响。规格应支持人格版本戳和候选版本切换，不能声称“放最后就完全没有 cache 成本”。

### 4.2 一个主体不等于所有受众读取同一份上下文

同一人格定义可被所有临时 worker 引用，但 memory visibility、工具权限、输入来源和输出目的地仍由任务 scope 决定。子代理短期拿到不同事实，不代表创建了不同人格。

尤其必须处理 **handoff 本身就是数据外发渠道**：主 loop 看过 owner 私密记忆后，即使群 worker 的 memory.search 只搜公开数据，也可能从主 loop 写的任务描述里拿到秘密。仅在检索结果上做 ACL 不足以解决这一点。

可行设计方向（需最终决定强度）：handoff 优先传消息 ID、目标 scope、允许访问的资料引用和标准动作类型；不把主 loop 的整段上下文复制过去。涉及私密资料的自由文本结果继承资料的可见范围，分享出去需要明确的分享规则或 declassification 动作。不能承诺完美语义防泄密，同时又允许无限制地把私密上下文摘要塞进公开任务。

## 5. 六个新矛盾场景问题

这些问题基于持续主 loop 已经确定的前提，不重问是否应该常驻、不重问 owner 关系或最低硬件。

### Q1. 群回复必须逐条经过主体审定，还是可授权临时对话 worker 直接代表它发言？

**场景：**十个群同时问问题，主 loop 正在思考一个长期方向。十个临时 worker 已各自准备好答案；若每份答案都返回主 loop 再生成一轮确认，主体队列会变成长尾瓶颈。若直接发出，两个 worker 可能同时对它的个人立场给出不一致回答。

**建议默认：**主 loop 对一段 conversation epoch 下发有限的发言委托；普通事实问答由 worker 按共同人格和权限直接投递，个人立场、新的长期承诺、跨任务冲突返回主 loop 串行决定。发言委托可撤销，有版本、目的地与有效范围；不能变成第二个无限自驱的聊天主体。

**要裁决：**你要求“它说的每句话都经唯一主体最后看过”，还是接受“主体委托的临时嘴巴”，只把真正改变长期意图的决定交回主体？

**取舍：**逐条审定提高连续性，但消耗更多模型调用和延迟；委托发言提高响应并行度，需要协议保证发言范围、人格版本、撤销和冲突报告。

### Q2. 单并发后端上，持续思考主 loop 与执行 worker 谁让出下一次推理机会？

**场景：**主 loop 每完成一次思考就立即发起下一次；三个探索 worker 也在等同一 API 的唯一 slot。若主 loop 永远最高优先级，探索永远无法产生结果；若一让就是长 worker 请求，主体又会在很长时间内没有下一次推理。

**建议默认：**保持主 loop 连续自驱，但其每次推理同样必须获得有限时长的 request permit；按可配置的公平份额和最大等待时间在主 loop 与 worker 间交替。主 loop 的存在与下一次推理 pending 都保留，UI 明确“等待推理许可”。不靠创建第二主 loop来解决，也不把持续模式改成固定分钟 heartbeat。

**要裁决：**在物理并发只有 1 的情况下，你是否接受主体短时间等待 worker 推理，以换取委派真正能推进？如果需要主体几乎即时持续思考，是否允许独立的小模型/独立资源组作为其专用后端？

**取舍：**共享同一后端需要公平份额，专用后端提高并行连续性但改变模型组合与硬件预算。任何规格都不能同时保证单物理 slot、主 loop始终占用、worker推理同时推进。

### Q3. 主 loop 已经看过秘密，能否把“理解后的摘要”自由写进群任务？

**场景：**主 loop 看过一封私人邮件，随后让群回复 worker“告诉大家我明天因某某原因不来了”。worker 没读私人库，但任务描述本身已经包含私人事实。检索 ACL 全部正确仍然发生了跨域披露。

**建议默认：**handoff 的数据来源和受众范围是协议的一部分；默认传引用和标准动作，不透传整个主上下文。私密来源派生的自由文本继承可见范围，跨域使用必须匹配已有分享规则；若用户愿意让主体自行决定分享，明确将这标成更宽松的模式，不能再宣称严格信息隔离。

**要裁决：**你要“主 loop 永远可以自行判断什么时候透露事实”，还是“它可以知道，但未经分享规则不能把这些事实交给公开 worker”？

**取舍：**自由摘要更像真人，严格来源边界更可审计；同一人格不要求放弃来源权限，反之给不同 worker 不同 ACL 也不会自动防住主 loop 的自由文本泄露。

### Q4. 自我改进可不可以改变人格、主 system 和它自己的委派协议？

**场景：**改进 subagent 认为主 loop 太犹豫，修改人格让它更主动；另一个分支改写 system 让它直接 shell；第三个修改 memory 检索摘要，导致它重新理解了过去的承诺。候选版本单独跑通并不代表替换后的同一主体仍保持用户想要的边界。

**建议默认：**允许 subagent 自主试验人格、提示词、技能与记忆策略，但稳定的主 loop 工具权限/协议由宿主执行，不接受人格覆盖。人格与提示词候选经过隔离回放和可读 diff，由明确的更新规则决定自动提升还是等用户。当前已生效版本、候选版本、失败证据均可观察；主 loop只选择/指派，不亲自修改文件。

**要裁决：**你希望“性格和价值偏好也能自行演化”，还是只允许它改进执行方法、人格变化需要你定？你接受它用不同人格候选做离线试验，但只保留一个对外生效主体吗？

**取舍：**可自动进化更符合自主生命感，却必须定义身份连续性和回退行为；固定人格更可预测，但限制了用户期待的某些自我改进。无论选哪边都不允许一次升级让主 loop越过已确定的工具职责。

### Q5. 两个 worker 对同一记忆或进度作了相反更新，主体何时应认为新状态成立？

**场景：**一个研究 worker 把“方案A不可行”写进记忆，另一个刚找到相反证据；版本 worker还原了工具环境，但主 loop 已按新工具可用继续派任务。若记忆/进度机制都在 subagent，谁负责通知主 loop目前看到的是提议、已提交事实还是过时快照？

**建议默认：**worker提交带来源、base revision、幂等键和状态的提议；记忆维护 worker负责合并、冲突标记与实体变更，持久层以原子提交返回 revision。主 loop通过read/save memory协议看到明确的已提交版本/冲突结果，不直接编辑数据库或文件。记忆索引尚未更新不能误报写入失败，环境版本回滚不能静默回滚外部已发生的行动。

**要裁决：**你更接受主 loop 暂时读到旧状态但不断推进，还是涉及已委派目标/承诺的更新必须等待一个明确提交点再继续？哪些进度变化必须立即打断当前思考，哪些可在下一轮合并？

**取舍：**最终一致更流畅，关键事实强一致更可靠；这个选择决定消息积压、冲突处理、memory read-your-writes 语义和UI“已记住”的真实含义。

### Q6. 主体异常退出后允许自动启动影子接管吗，旧主体恢复时谁仍是“它”？

**场景：**主节点卡住，监控误以为死亡，于是启动一个新的主 loop；旧节点随后恢复，两边都根据同一个人格和历史继续指派。即使每个进程自身单线程，现在已经有两个“我”。某个对话 worker 还持有旧主体的发言委托。

**建议默认：**同一主体拥有唯一 epoch 与可验证租约；接管产生新 epoch，旧 epoch不能再指派、更新共享记忆或代表主体发言。新loop从已提交边界恢复，不重放已确认副作用；UI把恢复视作同一主体的新运行段。无法确认旧主体被隔离时，以保护唯一性为优先，而不是静默双活。

**要裁决：**当节点之间失联时，你更重视“它始终有人继续工作”，还是“绝不同时存在两个可行动主体”？是否允许失联旧节点继续离线思考，但禁止其对外派发或写入共享状态，重连后仅将结果作为候选提案？

**取舍：**优先可用性可能出现双重承诺与重复动作；严格单主体会在不确定故障期间等待。允许离线候选思考可以保留探索工作，但不能把它宣传为两个主体都在合法延续同一当前意志。

## 6. 最低的UI验收条件

- 同时十个渠道来消息，只显示一个主体连续状态；子任务并行不产生十个独立人格。
- 主loop在模型未实际执行时显示排队/离线/恢复，不播放伪造思想流。
- 主体可见的公开行动说明可追溯到真实事件，无法确定的信息显示未知。
- 群聊历史/公开活动页面不出现owner私密来源、私钥、未授权handoff正文或其他群上下文。
- 人格变更显示版本与适用范围；临时worker不能自称已改变主体的长期偏好。
- 高优先消息改变同一主loop的处理次序，不启动第二条主逻辑链。
- 发生恢复时用户能看到上个已提交点、恢复原因、继续执行的任务及投递不确定项。
- 群聊普通用户无需理解worker、slot或snapshot，也能知道它是否收到请求、是否在做以及在哪里取结果。
