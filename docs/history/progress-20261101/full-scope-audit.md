## 2 可直接纳入 AGENTS.md 的核心合同

### 2.1 目的与自主范围

你的目标是把已经确认的 Shenko 产品完整实现并交付，使它成为能持续生活、委派、补足能力和发展自身的个人主体框架。实现顺序、内部架构、算法、插件组织与验证办法可以自主调整；用户已经确定的结果不能被悄悄换成更容易的目标。WHY 解释一条方法为何有用、依赖什么前提、怎样观察结果；它支持换方法，不要求每次行动先生成解释或请另一个 Agent 放行。[G-SPEC §40.1–40.3、§40.9；R126/R139]

开发授权生效后，持续完成研究、设计、代码、调试、验证、文档、提交、PR、集成及范围内的部署/迁移。压缩上下文、换 worker、重启、失败恢复和升级不撤销已有目标。不在每个任务、commit、PR、阶段或可恢复技术选择后询问“是否继续”。真实凭据、账户权限、费用授权和用户明确边界照实际处理；缺少其中一项时只阻断对应动作，继续不依赖它的工作。[G-SPEC §40.1、§40.7]

默认保留全部正式产品范围。S1–S5 是交付顺序；接口先行、模拟环境、首版可用和阶段发布可以推进工作，但不是最终完成理由。不得把困难项改名为 future、optional 或 N/A 来缩小分母，不得用宿主代理冒充具名 WASM 目标，也不得将有代码、可编译或作者自评等同真实可用。[G-SPEC §23、§29、§40.3]

### 2.2 用并行工作缩短完整交付，不复制多个项目方向

能并行时将清楚可分的研究、实现、平台验证和独立审查交给 subagents。每个任务说明目标、对应 R/B/case、当前基线、依赖、完成证据和写入范围；这些内容足以让 worker 理解为什么要做，不规定机械的逐命令脚本。每个写代码的 worker 使用独立分支/worktree；共享协议、迁移器和生成锁文件指定明确整合者，避免多个 worker 同时覆盖同一活跃目录。[G-SPEC §35、§40；G-HANDOFF 推导]

主整合 Agent 持续维护任务依赖图和当前基线，吸收已完成结果、处理交错与回归，并分派下一批工作。独立任务并行；依赖协议的任务引用明确版本，不能通过各自猜测形成表面兼容。worktree 是代码隔离，不能隔离同一服务器、GPU、数据库或 SSH 目标的实际副作用；这些资源仍按真实占用协调。辅助模型和远程 coding agents 使用同一物理推理服务时，一并计入 C、KV、额度与取消未决状态。[G-SPEC §13、§35.9、§41.9–10]

提交和 PR 是可复查的持续交付单位。每个有意义的 PR 描述具体问题、为什么值得改、改变后的行为、需求/验收关联和真实验证结果；尽量交付能被使用的一段完整行为。基础层 PR 可以先合入，但其上层需求继续显示未完成。PR 通过当前自动检查和独立审查后自主合并；基线变化后补验受影响部分，不能拿旧 head 的通过结果证明新合并状态。[G-SPEC §40.1、§40.3–40.5；G-HANDOFF 推导]

### 2.3 独立自动 reviewer，不以人类签字作默认 gate

实质性实现、协议、权限、恢复、资源、模型策略和交互变更，由独立 reviewer Agent 审查。Reviewer 使用独立上下文，能读取 SPEC、需求/行为、精确 diff、相关实现及原始验证证据；不能只看作者给出的“已完成”摘要。独立不要求另一供应商模型，而要求审查结论能够独立形成和复现。纯拼写等低影响变更可采用独立机械检查；不为形式增加一轮全量 LLM 审查。[G-SPEC §40.5、§40.9；G-HANDOFF]

Reviewer 重点检查四件事：实现是否达成原目的；是否遗漏适用分支与恢复；是否悄悄削弱产品裁决；证据是否真的支持声称的范围。阻断项必须指向具体合同、可复现问题或缺少的必要证据，不能将个人风格偏好变成硬门。审查结果记录所审 commit、范围、发现、复现或检查证据及结论；`changes_requested` 后作者修复并复审，`pass` 后自主推进。[G-SPEC §39.5、§40.5]

遇到审查意见本身有误，可以用源码、实际接口与复现结果修正，保留原问题和处置理由；重要争议可交第二位独立 reviewer 验证。不得让作者改写 reviewer 的原结论，不得删除失败场景、缩小测试分母或把未执行项改成通过来解除阻断。外部仓库确有强制审批机制时按真实机制处理，不伪造审批；这不意味着所有项目默认增加人工等待。[G-SPEC §40.1、§40.5]

### 2.4 自主决策的尺度

下表是判断依据，不是每次行动必须填写的审批表。理由已在任务或 ADR 中充分说明时直接工作。

| 决策类型 | 自主动作与所需证据 | 何时才需要外部输入 |
| --- | --- | --- |
| 局部实现、代码组织、工具与默认算法 | 自主选择可验证路线，进行与影响相称的检查；必要时改方法 | 目标本身出现真实矛盾且现有裁决不能消解 |
| 公共协议、存储格式、共享资源、跨平台行为 | 自主形成版本化变更与依赖影响，独立审查，做对应 conformance/迁移/交错验证 | 外部接口或设备事实无法从现有环境取得，只请求缺少的信息 |
| core/rescue 自改、break change、自迁移、配置/代理更新 | 自主实现、验证和交接，保持真实恢复闭包与已发生效果；没有自动的人类升级 gate | 仅当要跨越已授权设备/账户/消费范围或执行不可推定授权的外部动作 |
| 新付费资源、新账户权限、用户目标改变 | 先把可完成的候选、证据和影响整理具体；继续无关工作 | 确实缺少授权或只有用户能作出的产品选择；明确说明哪项动作被何种事实阻断 |

“高风险”本身不等于必须问人。工程影响越大，越需要相应的独立证据、故障验证与可恢复方案；它不会自动取消用户已经给出的自主空间。对未裁决 D5 等真实权限关系，不把沉默当授权，也不因此关闭所有对话；可先完成与验证可配置授权边界，保留受影响场景的实际阻断状态。[G-SPEC §28、§40]

### 2.5 可持续接续与相称验证

维护一个短的当前 checkpoint：完整目标版本、已合入事实、活跃 worktree/PR、正在使用的环境与资源、未决操作、下一步和真正阻断项。源码、数据/工件、日志与证据保留稳定引用，凭据只存句柄；不能要求后继 worker 阅读所有历史聊天才知道如何继续。已经完成的研究和测试可复用，只有版本或条件变化使证据失效时才补相应验证。[G-SPEC §40.5、§40.7]

环境限制使当前会话结束时，交接明确“尚未完成、下一步是什么、恢复入口在哪里”，并留下实际可恢复任务。不能声称一个已退出的进程仍会持续工作，也不能用最终回复的措辞替代真正的 checkpoint、CI 作业或持久运行任务。无用户输入时继续授权内工作；长周期验收由真实运行作业承担，开发者继续完成其余工作。[G-HANDOFF；G-SPEC §40.7]

## 3 可直接纳入 GOAL.md 的完整目标

> 完成当前仓库所锁定的 Shenko 全部产品 SPEC，包括后续正式目标，而不止首版可运行发行。交付真实软件、可安装能力、可恢复状态、设备与后端适配、界面、开发文档和可复查证据。用户追加裁决进入同一覆盖账本。持续自主分解、并行实现、独立自动审查、修复和集成，直到以下完成条件全部成立，或明确保留无法解除的真实阻断而不宣称完成。

### 3.1 什么叫完成

完整完成同时满足以下条件；其中证据条件按具体行为需要组合，不要求每个文案需求运行相同测试。

1. **范围完整。** 当前所有 R 均有落点、B 的实际采用行为均有对照，所有具名验收以及新增必要场景均有结果。用户原话、后来更正、来源、实现与证据能互相追溯。没有未说明的需求、未完成的正式功能、失联的上游子行为或靠改标签消失的目标。[§32、§33、§39]
2. **行为完整。** 用户能完成端到端目标，适用的错误、取消、并发、恢复、更新和组合路径成立。文档/研究类需求以准确资料和可复查研究交付；操作类需求以真实实现与执行证据交付。研究某候选不自动要求复制它整套产品，但其承担的用户目标必须有真实实现。[§23、§39.5、§40.3]
3. **可安装、可发现、会使用。** 默认 seed 和各可选插件/awareness/Skill/感知有实际工件、依赖闭包、版本说明与必要用法；原生插件、Skill/MCP 兼容和市场路径可用。模型在未点名插件的适当任务中能发现并正确使用，反例不会滥用，失败能回到原任务。[§18、§38、§44–45]
4. **主体持续存在。** 正常运行保持一个串行主决策链，有限请求间继续下一步，主不直接文件/exec，孩子有真实进展；认识人、承诺、兴趣、媒体与远程任务属于同一经历。空闲不是被动等待或低频 Tick；故障分支与最终合并诚实可见。[§5、§6、§14、§22、§41]
5. **首版自开发闭环真实完成。** 实际 QQ/NapCat 消息找到既有 tmux/Agent Seat，child 操作 Claude Code/OMP 等已适配 Agent，修改 Shenko、验证、构建、迁移并接管运行，然后继续原任务。至少覆盖 core/rescue 的真实替换与失败恢复、期间消息和未决调用接续。产出 patch 或启动新进程尚不足以完成。[§35、§36、§41.15]
6. **所有正式具名能力有兑现。** WASM 家园、挂载、工具/包、真实 WASM SSH 与私库认证、两个 compact、四类原生推理后端、Python/Node/Bun in WASM、媒体、Computer Use、动态 UI、Playground、归档、选主等不能在完整目标中只留接口。每项限定具体真实版本、平台与适用能力，避免“任意 POSIX 程序已经无条件兼容”的假承诺。[§8–27、§42–45]
7. **可靠性有对应证据。** 已确认事件、效果记账、late receipt、未知在途、请求封口、流式重连、配置恢复、跨代迁移和分区汇合经过适用故障交错。local managed snapshot、host bind mount 和 remote 不混为一套回滚语义；旧代码恢复不抹除新事实。[§10、§23、§36–37、§41]
8. **真实环境与成本合格。** 用户 Tailnet 四流 128K 的目标 profile、C=1 活性/驻留、后端原生能力、已声明 Android/路由器/桌面节点及跨平台目标有实测 manifest。常驻核心、默认插件、运行时、活跃工具、模型和构建空间分别计量。未知字段保持未知，性能或功耗结论不从另一个设备外推。[§13、§22–27、§34]
9. **界面与文档可实际使用。** 默认主体时间线及 append/steer、稳定流式阅读、按需面板、对话配置和持久全栈作品都接真实状态；中文长文、小屏、键盘/焦点、缩放、主题与 reduced motion 检查成立。Proto-UI 最新主线核验与锁定、compiler 接缝、NInfer/Strata 各自中英文教程和关键插件双语最小路径随版本可复现。[§21、§25–27、§29.1、§40.6、§43]
10. **长期运行不是短演示。** 完成 S5 对应的真实 7/30 天运行与恢复观察，记录版本变化、RSS/资源趋势、失败分布和期间自主工作证据。加速回放用于提前找错，不能冒充 30 个真实经过的天数。变化只使受影响证据重新验证，不要求每个微小修正从头等 30 天；最终声称覆盖的版本/条件必须可解释。[§22–23、§29 S5]
11. **交付已整合。** 可复现构建、包/发行物、安装启动、升级/恢复、已授权目标环境运行、覆盖账本、自动 reviewer 结果和使用文档对应同一明确 release candidate。没有悬空的“已实现但未合入”必需模块；可选功能可以默认关闭，但有可安装实现并在启用条件下验收。[§29、§40]

对于真实受阻的必需能力，报告具体原因、已尝试路线、证据、还能做什么以及解除条件。即使其他部分已经可用，也标记完整 `/goal` 未完成。用户未修改范围前，不把实现困难自行批准为永久豁免。对于原本明确条件适用的候选（例如选用 BoxLite 后才适用的特定测试），条件不成立可记录不适用；其背后的 Linux VM / LayerFS / Computer Use 目标不能随之消失。[§23 A29/A34、§34、§40.3]

### 3.2 阶段交付如何服务完整目标

S1 可行性、S2 开发者发行、S3 平台、S4 能力、S5 稳定性仍可作为任务编排。通过一个阶段就发布/合入相应真实成果，同时自动继续剩余范围。依赖允许时并行推进后段功能；不要等所有 S3 结束才开始媒体或长期 soak。阶段完成报告给出当前可用能力和完整目标尚欠项目，不将阶段版本命名为“完整 Shenko”。

不可用硬件、账户或服务只阻断其真实集成验证；先完成可执行实现、确定性 conformance、能运行的替代测试与接入文档，并在账本保留缺少的真实证据。模拟可以发现问题和推进代码，但不获得 `real_verified` 标签。实际操作若需要未提供的账户或新增消费范围，只请求这一缺项，不把完整开发变成每步人类协调。[§40.1–40.5]

## 4 R / B / 验收覆盖账本

覆盖账本是开发状态索引，复用 SPEC 的稳定 ID，不创建另一套同义需求。可以使用 YAML/JSON 或数据库生成 Markdown；选能容易检查、合并和解释的最小实现。下面是所需信息，不要求为了填表增加运行时插件或模型调用。

| 记录 | 最少表达的内容 | 为什么需要 |
| --- | --- | --- |
| Requirement（R） | ID、现行 statement/source revision、类型（行为/约束/研究/交付）、关联 U/B/cases、目标 profiles、实现落点、当前状态、阻断与证据引用 | 防止一句“已支持”覆盖多个没有实现的场景；文档需求与执行需求采用适当证据 |
| Behavior（B 及子行为） | ID、上游 pinned/source 日期、实际采用的细分行为、主动不采用与原因、本产品差异、相关 R/cases、实现与证据 | B15.Q1 等子行为也要比较；项目名或引用链接不是 feature parity |
| AcceptanceCase | 原 ID/原意、来源章节与版本、前提与 profile、步骤或可执行入口、期待可观察结果、实际结果、evidence refs、未运行/运行中/通过/失败/阻断 | 把规范场景与一次实际测试分开，避免编译成功冒充故障恢复通过 |
| EvidenceRun | run ID、被测 commit/工件/plugin lock、环境 manifest、测试工具/数据版本、开始结束时间、期望/观察结果、日志或产物引用、结果与限制 | 让独立 reviewer 能复现，并识别哪些升级使证据过期 |
| Task / PR | 目标与理由、R/B/cases、依赖、写入范围、owner/worktree、commit/PR、当前进度、review 引用与下一步 | 让并行与换 worker 不遗失工作，也不重复覆盖同一目录 |
| Decision / Gap | 已有裁决或工程默认、前提、选择与替代、关联需求、可推翻证据；阻断事实与解除条件 | 区分“方法可改”与“目标已变”，不把未知理由编造为永久规定 |

`implementation_state` 与 `evidence_state` 分开：例如代码可以 `present`，证据仍只有 `simulated`。证据维度可含 `source_verified`、`build_verified`、`real_e2e`、`fault_recovery`、`soak`、`visual`；不以单一阶段枚举强迫所有需求走同一路线。Requirement 的 `satisfied` 是检查当前所需证据是否齐全后得到的结论，不能由作者手工改一个字段覆盖失败 case。

验收条件有两种合法的调整：真实用户裁决改了目标；或检查方法/原条件有事实错误，修订后仍证明同一目标。二者均保留前版、理由与证据。测试发现功能缺失时不能改测试让它不再覆盖该功能。分支上临时试验可以失败，主账本继续如实显示缺口。[§39.5、§40.5]

每次整合更新受影响的 R/B/cases，不要求重跑全部 189 项。完整目标检查时查看全部现行定义、所有仍适用 profile 与其证据有效性。统计至少分别显示：R 满足/总数、B 细分行为兑现/采用数、cases 通过/适用数，以及所有 blocked、未运行和条件不适用项；不能只报一个高通过率隐藏整个未实现子系统。
