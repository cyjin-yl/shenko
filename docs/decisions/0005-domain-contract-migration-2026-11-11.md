# 0005 分域规格与 Why：退役根单体正文

状态：采纳；文档迁移候选，不是产品实现或运行验收。

## 来源与决定

用户于 2026-11-11 明确要求：

> SPEC.md 和 WHY.md 即将被弃用了。它们的功能应该完全拆散到 docs/ 中。原有文件则留作导航。引导 Agent 去使用 doc 中 spec 和 why 相关的内容，并告知可以使用 INDEX.md。而原有 INDEX.md 和其他旧 docs 内容，也需要完全被更新以适应 SPEC 和 WHY.md 被弃用了的事实。

> 完整合同见 SPEC §50.4 这种类似说法需要全部抓出来，导向更具体的文档了。因为 SPEC.md 将不复存在。

这里“将不复存在”按前一条的明确导航要求理解：根文件不再承载规格或理由正文，保留短导航。上述原话是本次迁移的来源，不替它编造 U 编号。其他尚待登记的产品新决定不在本次机械迁移中冒充已整合。

## Why

读者需要直接找到一件事的意图、前提、可观察效果和可变通边界，而不是在一份超大 SPEC、另一份 WHY 和领域说明之间来回拼接。领域拥有者应能维护同一处的行为和理由。索引负责发现，不成为第二份权威合同；校验器负责保全事实，不阻止合理修订。

## 现行权威关系

- 最新明确用户决定控制目标。现行合同位于 [各领域文档](../INDEX.md#领域合同)，Why 就近维护。
- 根 SPEC/WHY 仅导航；旧章节数字作为来源标识保留。内容引用必须直接链接到具体文档和锚点。
- 原文与历史证据保留在不可变归档及 Git 历史中。旧的“根文件前缀不可改、只能追加”维护方法退役，不妨碍新的目录结构；原话和既有义务不能被静默抹掉。
- 既有认知裁决、产品范围、真实权限及代码/模拟/真实运行的证据区别不因搬迁改变。迁移不是对这些设计的一次重新批准，也不是宣布实现完成。

## 保全与迁移方法

[contract-migration.json](../contract-migration.json) 记录源 commit、原件 SHA-256、字节数、每个连续源块与目标路径/锚点。原件取自 `ec37e7b458cd9243892763d75da716c1e126e435`，归档不重写。每块保留文本与表格义务，仅转换阅读路径；用户原话保留原字节。领域间交叉引用直接指向拥有该合同的文档，而不是复制另一份定义。

[需求索引](../requirements/README.md) 的 schema 2 为每项保存新文档、真实行号和当前来源行；`migration_source` 保留旧来源。R/B/Ref/case ID 与 coverage 分母均不变，行号变动需要同步。旧 source_row 中的引用只作为原始证据保留，不是建议当前读者使用的路径。

历史来源、已发布证据中的旧路径与引文不作追溯性改写。它们由原 commit 解释；现行入口与有效指引不能继续依赖根单体。

## 验收与边界

- 每一个源字节都归入连续、无重叠的迁移块；每个目标有实际内容与稳定锚点。
- 四类机器索引、coverage 和原话保全检查不能因搬迁减少分母。
- 从 AGENTS、README、Skill、INDEX、领域合同和默认认知材料进入时，能找到当前具体规范与 Why。
- 文档检查不能冒称运行验收。依赖单体 SPEC 的运行时消费者必须同步迁移；未经构建或真实运行验证的改动明确留在候选状态。

本决定取代 [0003](0003-spec-governance-2026-11-06.md) 中关于根文件不可变前缀的维护方式，保留它的认知读法与历史依据；其他产品行为按所在领域的现行裁决解释。
