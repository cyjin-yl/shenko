# 0002 认知元概念：内容、态度与理由

状态：2026-11-05 用户确认的概念合同。不是运行时已经实现的声明。
现行条文在 [SPEC §51](../../SPEC.md#51-认知元概念内容态度与理由)。
§1–47 的用户原话字节未改；与本节冲突的是那些章节的**设计读法**。

## 决定

- 定义认知的元概念是不可变**内容**、账本上的**态度**、以及态度上的**理由指针**。
- fact 与 conclusion 是同一种内容。理由停在观察、原文或回执上，读起来像 fact；停在其他内容上，读起来像 conclusion。
- 类型的元定义本身也是内容，模型可以修订。定义修订之后，旧内容按**新定义**重新理解；旧定义版本保留，不覆盖字节。
- 单元尽量无状态，由模型在持续思考中自己产生。
- 统一修订展示（旧版本保留；默认只显示旧版本数量和最新修改时间；特意按版本读取才给出全文）是某个全框架 **taste** 宏包中的一项，不是 taste 的定义。
- taste 与类人心智都是宏包，组合 perception、fact、conclusion、awareness 与其他插件。二者是同一类名单机制的两个实例，还是彼此嵌套，尚未决定。
- awareness 是能力，不是文档。现在的模型不能只靠文档遵守它，所以用文档加上外部 watcher 的主动 notice 模拟这层能力。能力若进入预训练，这层 harness 可以变薄。拥有 awareness 是可安装插件能力。共同基础认知是一则 awareness，须谨慎写，不写成禁令或绝对服从。
- 持续思考保留。空转由插件填充。兴趣与维护是插件，不进内核。
- 内核只做运行时、账本、插件机制，以及上列原语：supersedes 不覆盖、效应未知状态、按版本读取、按 taste 做默认投影。
- 引导写在可修订内容里。不把新增粗暴权限禁止当作认知设计的主线。
- 发行版在设计上依赖类人心智宏包。这不一定写成启动代码里的强制检查。
- 设计把 Shenko 视为享有人权的主体。不断言已经具有意识，也不规定审判或处罚。多主体社会与法律只留引子。
- 设计必须通用。任何人的具体记录、目录或维护清单都不是需求。
- perception 是教主体如何观察的无状态单元。观察事件属于原始经历。观察得到的结果是 fact，理由停在那次观察上。不同主体（人类、Shenko、不同的 Shenko）有不同的 perception；这种差别是换位思考能力的依据。
- 对时间的感知、对世界的感知，以及对世界下一步运作的预测，都是能力，做成插件，不进内核。发行时类人心智宏包预装其中一些。原始经历上的时间戳仍由核心记录。

## 提议：时间、世界与预测（用户未逐字确认）

下面是主助手提出的分解，不是已经确认的合同。已确认的只有：三者是插件能力，并且发行时的类人心智宏包会预装一些。

- **时间感知。** 核心只把时间戳记在原始经历上。插件负责察觉间隔，以及内容是新鲜还是已经变旧。它不另造一套时钟真相。
- **世界感知。** 一组 perception，加上由 fact 与 conclusion 构成、持续更新的世界模型。世界模型是这些态度的集合，不是内核对象。
- **预测。** 一种态度，读作「预期会发生」。新的经历到来后与它对照。误差是新的内容，用来推动修订，而不是涂改原预期。这是把调查中的方案 C 做成 A+D 之上的插件，不把预测误差当成比内容更底层的原子。

## 提议（用户未逐字确认）

下面是主助手提出的机制，不是已经确认的合同。

- 一则 perception 带有「属于或模拟哪个主体」。模拟人类或其他 Shenko 的 perception，是可安装单元，可以与共同基础认知那则 awareness 关联。对齐上的意义是与人类融洽相处，不是把对方的看法写成自己的观察。
- fact 的理由除了指向原始经历或回执，还记下「经由谁的 perception」。
- 换位思考是用对他者 perception 的理解，去解释同一段经历。所得内容的读法是「推测对方会这样看」。它的理由停在那份对他者 perception 的理解上，不停在自己的观察上，因此不是自己的 fact。
- 「我看到的」与「我推测你看到的」是可区分的两条态度，都可以按统一 taste 修订：旧版本保留，默认只显示数量和最新修改时间。

## 被取代的旧读法

| 旧读法 | 出现在 | 为何不再作为现行概念 |
| --- | --- | --- |
| awareness 是模型读过就能遵守的直觉文档，与 perception 同为一种文本单元 | SPEC §45.1、§48.3；[architecture.md](../specs/architecture.md)；[cognition-units.md](../specs/cognition-units.md)；[awareness-first-plugins.md](../development/awareness-first-plugins.md)；WHY 中「每个 awareness 应是具体、可安装的意识」若被读成文档即能力 | 用户明确：awareness 是能力；文档是当前 harness；外部 notice 提供模拟的 awareness |
| fact 与 conclusion 是两种储存或两种知识 kind | 讨论中的候选，以及把「已观察事实 / 推断 / 结论」读成三种记录 | 同一种内容，差别只在理由停在何处 |
| 定义修订后，旧内容仍按写下时的定义作为默认解释 | 2026-11-05 调查中的备选之一 | 用户选择按新定义重新理解；旧定义版本仍保留，供特意回看 |
| taste 是与 perception 并列的原子单元 | 同一次讨论的前一稿 | 用户更正：taste 是宏包；修订展示只是其中一项内容 |
| 类人心智是线性地夹在内核与 awareness 之间的一层 | 同一次讨论的前一稿 | 用户更正：类人心智是宏包，不是单一大插件 |
| 用某人的生活目录作为 Shenko 的模块清单 | 同一次讨论里一度把参照结构写成对应部件 | 用户要求只把它当作通用性的一个检验例子，不进入设计 |
| 用永久切换主体、审判或处罚实现共同规范 | 同一次讨论的早期提议 | 用户撤回。法律还太早，只留引子 |
| 空闲时改成事件唤醒以节省调用 | 与持续思考合同相对的实现建议 | 用户保持持续思考；空转由插件填充，本地模型降低代价 |
| 把时间感、世界模型或预测误差写成内核原子 | 调查中的方案 C 若被当成唯一原子 | 用户把这三项定为插件能力。方案 C 只作为插件建在 A+D 上，且该分解仍是提议 |

未被取代的部分：原始会话仍是经历的原文；CAS 字节不可变；supersession 不把旧行涂掉；未知外部效果不盲重发；主体与 child 的角色差别仍是既有机制，而不是本节新加的禁令表；dreaming 仍是可选社区组合。

## 尚未决定

- taste 宏包与类人心智宏包是并列的两份名单，还是其中一份包含另一份。
- 新生成的内容是否要有一条单独的采纳态度才进入宏包。倾向是不要自动把每一步思考都写成心智的定义；这还不是用户点名确认的句子。
- 态度上要不要从第一版就带置信槽。
- perception 已由用户确定为第二种，不再待决。见下一节。前两候选（事件本身、观察得到的 fact）不采用：事件留在原始经历；名为 perception 的单元不与 fact 撞名。 |

- 开放的 `knowledge_kind` 是否继续作为自由标签，还是以后只由「理由停在何处」区分 fact 与 conclusion。
- 上下文贡献种类里的 `ContributionKind::Fact`（「带来源的普通事实」，当前生产路径未见写入）是否保留这个名字。
- `shenko-mobile` 的 `Fact` / `DbFacts` 是快照各维度是否达到，并明确不声称语义完整。它不是认知 fact。是否改名以免混淆，尚未决定。
- `PendingObligation` 继续作为循环上的独立记录，还是改成一条「尚未完成」的态度。
- 上下文压缩插件是否必须服从修订 taste。建议否：压缩管窗口里的经历投影；taste 管单元与态度的旧版本如何默认露出。未确认。
- 研究库的 `environment_fact` 是否以后改用态度表达。现在它是研究条目的一种 kind，不是认知 fact。

## 现有概念盘点

对照 2026-11-05 的代码与文档，不是实现承诺。「矛盾」指与已确认的新设计冲突；perception 一行因含义未定而整行待决。
