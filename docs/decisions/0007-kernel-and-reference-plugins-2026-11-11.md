# 0007 内核九条与参考插件

状态：采纳；文档候选。内核合同是目标行为，不是实现完成或运行验收的声明。

## 来源与决定

作者在 2026-11-11 的一次对话中审视了当前架构，得到两点判断：承重的骨架（原子步、回执、单写者）是对的；但扩展机制有多条并行的路，名义上的小内核与实际承重的代码不一致，项目的增长速度超过了一个人能掌握的范围。作者随后说：

> 也许我们应该用奥卡姆剃刀统一一下逻辑。

助手据此从源码和作者此前的决定中重新推导出九条内核候选，并以页面形式逐条给出理由与当前实现状态。作者看过之后说：

> 我同意哦。全面改写吧。所有文档都修订顺便修改实现代码。

以上两段是本决定的逐字来源，不为它们编造 U 编号。

作者此前在对话中还作出过下列决定。这些内容由助手转述，不是逐字引文，原对话未能取得；取得后按实际来源补充并核对。

- 框架不应规定太多内容；感知、觉察等做成可安装的插件，而不是核心。
- 自我改进中什么算“更好”，由主体自己定义；这个定义可以被推翻，但不应太容易。
- 元 awareness 与元感知默认安装，它们各自仍是普通的 awareness 与感知；其他元层同理。
- 主体自检回路的退避参数由主体自己设定。
- 看门狗可以是备用节点，也可以就是本节点；Shenko 不要求两台机器才能工作。
- 异地副本是可选的；不同节点之间共享并发上限与推理槽信息。
- 网络分区期间，各节点怎样划分共享的并发上限由主体自己决定，从保守的均分开始。
- 从规格中拆出一份小的内核规格，其余作为参考插件；每一条都带 Why，让实现的 agent 可以变通。
- Why 采用六栏：意图、前提、可观察效果、灵活边界、失效条件、来源。

作者曾认可过一版九条候选，但那份清单在本次对话时已经找不回来。现行的九条是重新推导并经作者同意的版本，不声称与原清单逐条相同。

## 决定的内容

1. 新增[内核合同](../specs/kernel.md)，规定九条不变量，每条带六栏 Why 与当前实现状态。
2. 判据只有两点：没有它，别的部分就不能被安全替换；它只检查结构，不判断意思。
3. 其余 30 份领域合同保留原有义务与所有权，各自在开头标明相对内核的定位：承载某条内核不变量，或者是建立在某些内核条目之上的参考插件。
4. 扩展机制统一为“一个门，两个架子”：一个生命周期，能力目录与钩子图两处登记。
5. 代码按[内核收敛计划](../development/kernel-convergence.md)分步向内核合同收敛；每一步在同一个改动里改写与之冲突的现行条款。
6. 新增只检查结构的[依赖边界检查](../../scripts/check_kernel_boundary.py)，以当前状态为基线，只允许违例减少。

## Why

项目在不到三周里增长到约三十个 crate、约二十九万行 Rust，由许多 agent 并行写成。规格按领域拆分之后，每个领域都有了自己的合同，却没有一处回答“哪些是不能动的”。结果是每个领域都可以合理地把自己的状态放进账本、把自己的内容接进主体，内核在名义上很小，实际承重的代码却越来越大。

一份很小的内核合同给出稳定的参照：实现者知道哪九件事不能破坏，其余的都可以按环境变通。六栏 Why 让这种变通有依据，而不是靠猜测作者的意图。

统一扩展机制是同一把剃刀的另一面。入口只有一个，才能随时回答“是谁在影响主体的这一步”，主体才能安全地给自己安装和编写新能力。

## 边界

- 本决定不删减、不降级任何需求、行为、来源或验收；覆盖账本的分母不变。
- 领域合同里与内核合同不同的条款列在[内核合同的差异一节](../specs/kernel.md#与现行合同的差异)。在对应代码落地之前，这些条款继续描述实际行为。
- 输出协议仍是内核 ABI，与 [57.1](../specs/subject-runtime.md#spec-57-1) 的既有边界一致。
- 起草本决定与内核合同的会话无法取得 Rust 依赖，因此没有编译或运行产品；本次改动中的代码只有一个 Python 结构检查。内核合同里的“当前实现”来自对 `dd28003` 源码的阅读，不是运行证据。
