- 编译与解释本身正在成为 agent 循环的瓶颈。理想情况下，循环的每一环都应该由 agent 自己改进和提效，包括编译器和工具链。

## 1 工具取舍：通用组合优先，特化封装有据

**意图。** 子代理拥有 REPL、WASM 家园、插件和远端座席等通用执行环境。默认让它在这些环境里写脚本组合能力，不为每个动作再包一层专用工具。专用工具只在通用组合明显更贵、更危险或更不可靠时才值得做。

**判据。** 一项能力满足下列任一条时，作为专用工具或插件提供：

- 需要一次构建、反复复用的全局状态，例如全项目索引、依赖图、长期缓存。脚本每次重建会重复付出这笔成本。
- 是跨多个文件或系统的事务性变更，需要原子提交、回滚或一致性检查，例如大规模迁移或模块化。
- 产生外部效果，需要回执、幂等键和未知结果对账（[内核 5](../specs/kernel.md#kernel-5)）。
- 需要授权、凭据或隔离边界，而这些不能交给任意脚本，例如渠道发布、支付、节点控制。
- 有可测的正确性要求，脚本组合实测反复出错。

不满足任何一条时，子代理应使用通用环境。若已有的专用工具在实测中不比脚本组合更省、更稳，可以由自我改进流程提议移除或合并，证据与移除理由一并保留。

**可观察效果。** 新增专用工具时，其登记（[§18.2 可使用性包](../specs/plugins.md#spec-18-2)）写明它满足的判据，以及与通用组合比较的证据或尚待验证的理由。使用审计（[§18.6](../specs/plugins.md#spec-18-6)）可以据此发现从未被选用、或总被脚本绕过的工具。

## 2 开发循环自身的耗时是改进对象

**意图。** 主体与子代理的开发循环包括推理、构建、测试、等待资源和传输，其中任何一环都可能成为瓶颈。§9.1 已经允许重写任何部分；本节要求主体能看见时间花在哪里，而不是只在人提出时才去优化。

**工程合同。**

- 每个开发或自我改进任务按阶段记录墙钟时间与资源消耗，至少区分推理、构建/编译、测试、等待调度或资源、外部传输。记录来自实际观测，没观测到的阶段保持未知。
- 主体可以把这些记录汇总为自己的循环画像，并据此提出改进目标，例如构建缓存、增量编译、更快的工具链、测试选择、并行或换实现。这些目标与其他自我改进一样走「提出→构建→验证→切换→观察→保留或回滚」，不另设通道。
- 工具链与编译器属于可改进对象（[§9.3](../specs/self-update.md#spec-9-3)）。替换或重写工具链时，验收比较的是同一任务在新旧工具链下的产物等价性与耗时，而不只是“能编译”。

## 3 不变的底线

「人类不再读代码」不能作为削弱验证的理由。代码可以没人读，但验证与作者分离、失败证据保留、真实运行与模拟分开（[§46](../governance/COMPLETION.md#spec-46)）仍然适用。重写一个组件比过去便宜，这只说明可以更频繁地重写，不说明可以少验证。
