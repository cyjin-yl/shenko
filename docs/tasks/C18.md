### durable quota ↔ broker/Store 贯通（2026-10-30，源码级、未验证）

本次把已合并的 typed quota 状态机接上真实 Store 账本和 RequestSeal 生命周期，全部位于
`feat/c18-broker-quota-20261029` 工作树。**本段为纯源码与新增用例记录：未运行任何编译、
测试或真实模型验证；以下行为描述是代码意图而非通过回执。**

变化面：

- `shenko-store` 新增 `quota.rs` 与 additive `quota_snapshots`/`quota_forecasts`/
  `quota_policies`/`quota_decisions`/`quota_pacer`/`quota_attempts` 表；所有写入走既有
  IMMEDIATE mutation line，没有第二个 JSON 账本。快照/预测/策略/决策按**已记录字节**
  绑定 provenance（同 id 不同字节即冲突）；预测要求其源快照已入库，决策要求策略
  revision 与所引预测均已入库。
- `admit_quota_send`/`arm_quota_send`/`cancel_quota_admission`/
  `settle_quota_attempt` 把 admit→arm→dispatch 串成真实事务：
  arm 在同一事务内为每个 quota window 写一行 attempt，并以本事务 `CommitRef` 绑定；
  attempt 行的完整键为 `(request_id, provider_id, account_scope_ref, window_key,
  commit_seq)`，settle 也按同一完整身份匹配；已 armed 的重放只核验原有行，不产生
  第二份 attempt；armed/unknown 取消保留 `[0, upper]` 直到同账本覆盖证明，armed 后用
  NeverDispatched 取消在任何幂等返回或 mutation 之前被拒绝；仅确实未发送（未 arm）
  mutation 之前被拒绝；仅确实未发送（未 arm）的取消释放预算。已 admitted 的 immutable
  send 在不同已记录 decision 下显式对账（保留 armed 行、计费历史、admitted_at 与
  pacing，绝不二次计费，覆盖不上则进 wait 而不是死锁；armed 历史独立于当前
  eligibility 合法存在）。`step.active_request_id` 是不可变的 sealed provider
  request，绝不改写：每次 wire send（含首次与每次 retry）用独立 send_id 做
  admit+arm，`quota_sends(request_id→send_id, send_seq, claimed)` 与 attempt 行在同一
  记录，且 `admit_quota_send` 在**同一 commit** 里写入 send→request lineage（预算
  与血缘原子诞生，crash 间隙没有不可找的 charged send）；AwaitingModel CAS 在
  **同一事务**里对该 request 的最新可 claim send（latest unclaimed 且 reservation
  非 Cancelled）做 admitted+armed 校验并置 claimed=1；gate 复用同一谓词选中该
  send，并把**选中的精确 send_id** 沿 `upsert_step_claiming_send` 传入 CAS 同事务
  校验+claim（claim_seq 记 durable dispatch 次序，绝不重查 mutable latest，另一
  worker 并发写的新 send 既不能劫持 claim 也不能锁死所选预算）；gate 仅在无可用
  send 时 mint 新 send_id，AwaitingModel 恢复按最新 claimed_seq send 绑定；Response
  观测与结算归属**本次 dispatch 的精确 send** 的 scope 与行，429 发送不结算，未
  claim 的 send 从未上 wire。claim 是持久派发授权，不是已发送证据：CAS 提交后
  submit 前 crash 仍保持 Unknown，不 unclaim 不退款。不发任何探测性付费请求。
- `try_upsert_step` 新增闸门：一旦存在任何 `quota_policies` 行，进入 `AwaitingModel` 的
  CAS 必须看到 `active_request_id` 的最新 send 已 admitted、`dispatch ==
  ArmedOrUnknown` 且未被 claim；claim 与 CAS 同事务提交。恢复或另一写入者无法绕过
  准入重放未知调用。没有任何策略行时闸门完全不存在，未配置 quota 的本地
  provider 行为不变。
- `shenko-subject` `execute_step` 接入完整通路：读最新策略 →（过期时）以已记录快照 +
  `quota_attempts` 全量重算预测 → decide/record → admit → arm → step CAS → broker.submit
  → 普通响应证据回写（仅当策略唯一确定一个 cloud scope；429 无头时记
  `observation_failed(RateLimited)`）→ ProviderTerminal 时按 usage 结算该次 attempt
  行。`quota_policy_wait`/`provider_exhausted`/`observation_blocked` 以 ≤30s 有界
  睡眠重新准入，不占 compute、不伪造推理；容量类结果如实报错；重新计算/再合格
  循环上限 32。模型选择仍受 seal 约束：admitted profile 的 `model_ref` 必须等于绑定
  模型，否则 MODEL_PROVIDER_BINDING_MISMATCH 而非静默换模型。
- `shenko-quota`：`QuotaPolicy.observation_sources`（按来源绑定 TTL 与 stale 用法，缺省
  等于不承认任何来源为证据）、`QuotaForecast.options`（记录计算所用参数，旧 JSON
  缺省拒绝 stale）、`Pacer::reservation(s)`、`policy_digest` 公开；`admit` 对已 admitted
  record 做显式 decision 对账。`shenko-broker`：
  `InferenceResult.quota_headers` 只保留 `anthropic-ratelimit-*` 白名单头（含 429 响应），
  让普通流量即可更新观测。`record_quota_decision` 同时核验所引 forecast 的源快照已
  记录、来源经 policy `observation_sources` 承认、且 options 与该来源项一致。
- `shenko` 二进制：`SHENKO_QUOTA_POLICY` 指向一个序列化 QuotaPolicy JSON，启动时
  `record_quota_policy`；不可读/非法即启动失败，不静默按无额度运行。

新增 9 个独立永久场景（`shenko-store/tests/quota_store.rs`，合成策略与额度值，每
  #[test] 一个行为输入）：armed 预留跨 reopen 保留精确 CommitRef 身份并拒绝矛盾取消；
  无策略时 AwaitingModel CAS 不受闸；有策略时 CAS 要求 armed reservation；未 arm 的
  NeverDispatched 释放；decision 所引 forecast 必须用 policy 承认来源的 options；
  admission 必须出示已记录 policy 字节；已 admitted 请求在新 decision 下对账保留
  armed 行与计费历史；settle 绑定完整 scoped 身份与提交；covered_through 折扣而不抹
  历史。**尚未运行**；父集成验证（真实 Store+broker 旅程与本地 Coder390，绝不接触
  云生产额度）由主控执行。

仍缺（#23 未关闭）：`covered_through` 目前没有真实生产者（API headers 无法证明覆盖
本地账本），statusline/admin 采集器未接线，主体可读 quota 视图与 §42.6 事件未做，
模型/跨 provider 路由只在已 seal 请求的准入节奏内生效（换模型仍需新 seal，
S0 阶段的路由选择未接），child/native 推理不经此闸（本切片只接 subject 路径），

对合并候选的独立审查发现，窗口预测原先丢失了来源和强制类型；本地 configured cap 或
过期 last-known 的零余额也可能被误报为当前 provider 耗尽。继续修复后，预测保留类型化
`provider_exhaustion` 证据；旧预测缺字段默认为 unknown。仅 fresh 的 provider 来源、
provider hard limit，且由直接 provider-reported remaining 或全为 provider-reported 的
capacity/usage 独立证明零时，period 与 replenishing 才能报告 provider 耗尽。重新协调后的
零余额本身不是证明；last-known、local/estimated 和仅因本地费用/reserve 而归零不冒称
provider 耗尽。本次源码及新增用例**尚未验证**；下述先前回执不适用于这个后续版本。

独立审查又发现，多窗口共同等待的较晚期限可能掩盖较早的 bucket refill：即使该零余额
仍在来源 TTL 内，经过已知 refill 后也不能继续断言 provider 当前耗尽。修复使决定在最早
相关窗口变化时失效，入场需重算；经过 refill 的旧零余额不猜测为已补满，仍保守等待或重观测。

当前永久新增场景按独立行为计九项：直接报告的空 bucket、跨窗口早 refill/自身费用等待、
local 的边际恢复、超过阈值切云、local 不可用切云、stale last-known 零、local configured
cap 零、混合来源重新协调出的零、旧预测缺少证据。原有 period 耗尽测试改用真实 statusline
解析的合成输入，仍是该既有场景。为遵守场景上限，移除重复的边际恢复/跌落、先前新增的
多 local 用例及单窗自身费用用例；跨窗口回归仍使用真实 forecast 的未反映自身费用，已有
forecast 测试也覆盖该费用计算。其先前运行事实不因此抹除，也不把测试函数数量当作场景数。
下节保留的是**原 PR94 候选**而非本次 merge 或后续修复源码的历史证据。
