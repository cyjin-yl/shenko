## 当前已具备与真实差距

本工作树的 #26 准备阶段候选修复了槽发布竞态：先独占创建与目标同父目录的随机 stage，完整复制工件并用 SQLite Backup API 备份数据库，再只调用一次原生不替换发布；不再先检查最终路径后复制、也不在失败时删除目录。已有空目录、非空目录或其他目的条目都不是可以覆盖的槽。复制文件与备份目标同名时拒绝覆盖；stage 不能置于 A 工件树内。阶段创建／复制／发布错误分别提供尝试的 stage 路径，发布错误还提供最终路径；最终路径及所有失败或竞争失败的 stage 不由协调器清理。stage 创建之前的输入校验错误没有 stage。stage 消耗的空间与后续排查／处置仍需实际恢复机制管理。

Linux/Android 使用 rustix 的 `renameat_with(NOREPLACE)`，Darwin 使用其 `RENAME_EXCL` 对应实现，Windows 使用 `MoveFileW`（不传覆盖或复制回退标志）；其他未确认平台显式返回 unsupported，不退回普通 rename。操作系统、内核和目标文件系统均须实际支持该原语；NFS 等远程文件系统中，rename 报错不能证明服务端未完成，因此必须检查 stage 与最终路径后再对账，不能盲删或盲重试。Windows 文档未在此确立目录移动的并发可见性保证，Darwin 文件系统能力、重解析点及各实际挂载行为也需另行验证；单次发布不是断电持久性承诺。

Linux 开发容器内，产品代码提交 `57c8d24` 对应的候选源在项目 ZFS 挂载上通过了 10 项 updater 测试。独立真实 `UpdateCoordinator` 消费者在基线 `f34e569` 观察到目标目录先于数据库出现；候选同样复制 1024 个文件，未观察到该不完整状态，并在双发布者竞争中保留一个完整赢家和一个内容、数据库一致的失败 stage。证据位于 `build/c21-slot-consumer-20261029/baseline-51161453/summary.json` 与 `candidate-950cbe6c/summary.json`。独立评审又发现合法的 `slot-a/../staging` 路径被错误拒绝，实际消费者的失败记录为 `build/c21-slot-consumer-20261029/relative-red-eac62fcd/summary.json`；后续修正应允许不需要在 A 内创建目录的已有兄弟路径，同时仍拒绝会在 A 内创建的中间路径。检查假定 stage 根及其祖先可信且不被并发替换，不构成 inode 约束。这只证明上述有界 Linux/ZFS 场景，不证明所有竞态、Windows/macOS 或断电，也没有接入真实运行时，不构成完整 #26／A39 的验收。
