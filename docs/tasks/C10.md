## 2026-10-29 依赖边按工件 digest 隔离的候选切片

`shenko-node` 的候选改动将依赖边绑定到 `(unit_id, revision, artifact_digest, edge_id)`，
闭包遍历、重解析和导出使用同一版本；相同 id/revision 的不同工件各自物化到含 digest 的
路径。已有的满足选择不会因再次导入而静默改选；新格式跨节点携带每个工件自己的选择，
已选目标缺席时保留精确引用并等待该目标，不能用另一个候选冒充。不同节点同一边的已选
引用冲突时拒绝该导入，原选择保留；这是待对账的版本选择冲突，不代表 provider 已激活。

Node storage schema 4 先校验旧安装的精确 fingerprint，再事务迁移 v3：旧 `unit_edges`
原行保存在 `unit_edges_legacy`；同 id/revision 只保留一个 digest 且边与声明一致时可保留
旧选择，多个 digest 或缺失/不匹配的旧边则标为 `legacy_ambiguous`，不猜原所有者。旧数据、
节点身份和历史不因迁移删除；同版本记录和 digest 边更新前会保留旧序列化记录。无关包的到达不会
自动解除此状态；`resolve_version` 可对**该精确版本**作新的本地解析而不改变 current，
无可选候选时仍保持歧义。也可导入不携带选择的 schema-3 authored 包重新解析，或导入
带明确选择的 schema-3 包采用来源的选择；导入可能改变 current，均不宣称找回旧选择。
推荐边的歧义仍可见；必需边的歧义使闭包未完成。导入结果分别披露输入决议和实际保留决议。

Unit transfer schema 3 同时显式绑定根工件与版本专属选择，不依赖包顺序；接收旧 schema-2 包时，由于旧包没有携带这些
选择，受影响边也显式保留 `legacy_ambiguous`，不能从包列表推断历史选择。新节点可接收
schema 2；旧节点无法接收/确认 schema 3，升级接收端后再传。checkpoint `0fa2b0f9` 的
Node 套件 10 项通过，真实 Node 的旧版本迁移、并发打开及 stale pin consumer 也有独立回执。
受控的 40,000 条旧记录迁移中途杀进程后，旧候选的 immutable preflight 拒绝了可恢复的

## awareness 已接入主体（2026-10-27）

此前 `AwarenessRegistry` 只有库与测试，没有任何生产调用者：觉察写下来也到不了模型。
现在主应用启动时装载内置种子与 `data_dir/awareness/*/AWARENESS.md`，每个 subject 步骤
用该步真实输入检索单元，并把命中的正文作为**易变的每步后缀**追加在稳定前缀（合同＋
人格）之后，明确写成"提供一种视角，不是必须执行的命令；可以采纳、改写或忽略"。稳定
前缀保持在前且是 context profile digest 的输入，因此每步不同的觉察不会反复更换 KV
窗口。停用的单元根本不注入；注入不触发任何分支，也不授予权限。

取用改为**有界全量注入**（合计默认 4 KiB，超出预算只列 id 与能力卡）。此前试过两个
方向的关键词检索，沙箱实测都失败：先看"提示词里的词是否出现在单元 id/卡片里"，真实
消息（"什么 都打不开了"）命不中；改成"单元自己的词是否出现在消息里"后仍然命不中
"网络"这个从未出现的概念词，导致单元没被注入、启用与停用结果几乎一样。按关键词检索
等于在最需要视角时把它藏起来，所以现在不做词匹配，选择交给模型。

单元只提供原则与视角，不写具体动作：写死步骤只在那几个处境里有效，还会让评测退化成
背台词。通用性、是否有效由真实沙箱的成效自测回答，方法与防作弊要求见
[内核零业务，能力优先写成 perception + awareness](../development/awareness-first-plugins.md)；
不得用禁用词/步骤词正则表代替判断。首轮实测数字、失败原文与未证明范围见
[local-model-and-awareness 证据](../evidence/local-model-and-awareness-20261027.json)。

这是接续任务，不要求重写已有代码。未合入候选由主控发布可取的 checkpoint 后复用；若候选尚不可取，先推进接口、独立实现或相邻可做项，不等待原作者在线。代码路径及实际候选会随后写入任务清单。
