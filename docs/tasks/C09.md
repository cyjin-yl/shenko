## 语义遗忘 intent 切片（2026-10-29）

`MemoryIntentKind::Forget` 此前在 `MemoryStore::commit_queued` 里被直接拒绝
（"forget requires a resolved target entry; not supported yet"），durable 的
forget intent 永远无法结算。本切片把它接上真实 Store 合同：

- `MemoryStore::accept_forget(intent, entry_id)`：forget intent 以它要退役的
  `entry_id` 作为 durable 绑定写入 `memory_intents`；同一 `intent_id` 重放
  复用原请求，绑到不同目标的同名 intent 在准入时被拒绝（沿用既有
  `admit_memory_intent` 身份规则），无 content_ref。
- `Store::commit_memory_forget(intent_id)`：一条 ledger 事务内校验 intent
  仍 `accepted`、kind 为 `forget`、目标 entry 存在且属同一 agent（forget 不是
  跨 agent 删除通道），把目标 `deleted=1`、`record_revision+1`、
  `updated_commit_seq` 落盘并把 intent 置 `committed`、写 `commit_log`。没有
  物理删除：§12.4 的 semantic_forget 与 erase 分开，原文、来源与
  `memory_intents`/`memory_intent_bindings` 事实全部保留。
- `MemoryEntry` 新增 `deleted` 字段；`search_memory`/`list_memory` 维持既有
  `deleted=0` 过滤（遗忘后默认回忆不再出现），新增
  `Store::memory_entry`/`MemoryStore::read` 可按 id 读回含已遗忘条目的原文，
  满足"原文引用可还原"与审计回查。FTS 走既有 update 触发器，无需删行。
- 目标不存在或属于别的 agent 时不提交、intent 保持 `accepted` 可重试：跨节点
  复制时 entry 可能后到，失败的 forget 不会静默吞掉也不会误标终态；entry
  已复制 `deleted` 列，cognition archive 原样携带遗忘事实。
- 复审修正（同日）：cognition 归档校验区分"生产 entry 的 save/correct/recall"
  与"引用目标 entry 的 forget"——Save→Forget 历史不再被 `entry_owners` 判为
  共享身份，导出与接收方校验都能通过；`accept_forget` 在返回终态前先比对
  durable 绑定，committed/failed 的 intent 换目标重放被拒绝而不是谎报终态；
  `write_memory_entry` 绑定传入的 `deleted`，未改动的 tombstone 重写或携带
  `deleted` 的新插入都不会把已遗忘条目静默复活。

仍缺的相邻事项：subject 输出协议尚无 `Forget` 动作，`settle_subject_memory`
仍只结算 `Save`；`Correct` intent 仍以"写一条 correct 记录"处理、没有
superseded 标记；主动 PMA worker、reset-to-best、外部记忆移植、空间处置仍未
实现。遗忘经库 worker 路径验证，非真实模型行为证据。

## MemoryStore intent 重放与恢复

同一 intent 的重复提交复用原 entry，输入不一致则拒绝；已提交或已失败的终态不会被
迟到的失败回写覆盖。恢复后可继续处理已接受的 intent；带 CAS 正文的 intent 保留完整
对象引用，并纳入认知恢复闭包。旧数据如果只剩 locator、无法证明完整摘要，不会凭空
补造引用。处理全部待办时也对账本地队列：另一 handle 或归档已将 intent 置为终态后，
本地不再长期报告它待处理；重复接受终态也会撤去该 handle 的旧队列项。上述是
`MemoryStore` 和 `Store` 的合同，不表示主体 CLI 已接入该 worker。

认知归档 schema 3 将 intent、其引用绑定和对应 entry 作为同一恢复单元；旧 schema 2 可读，但缺失
待处理 library intent 的完整引用时标记阻断欠账，不能确认可恢复。旧版读取器不理解
schema 3，须升级后再接收；不会静默略过绑定后给出 verified ACK。未知事实表亦拒绝。
冲突导入保留本地 intent 和绑定，也不提前发布该冲突请求的 entry；不把远端摘要嫁接到 locator-only 的旧请求。对象的
locator 可随节点变化，摘要、字节数和类型一致的重试仍复用原请求。

真实库消费者在独立的合成存储中验证了重开重放、冲突拒绝、终态保持，以及认知归档
导入后的正文引用和待处理 intent；真实 CLI 使用合成 HTTP provider 两次启动并干净退出，
重开后仍只有一个相同 intent 的 entry。真实新旧 Store 消费者确认 schema-2-only 旧版
拒收 schema 3、新版接收完整 schema 2 且拒绝缺少完整身份的旧待处理引用。证据分别为
`build/c09-memory-consumer-20261028/subject-7fa4d7bc/summary.json` 与
`build/c09-archive-compat-20261028/green-b673c8ea/summary.json`，对应代码 `684638f`。
这不是实际模型行为、真实用户记忆、物理断电或所有不同版本节点间归档兼容的验收；
完整 C09 仍未完成。

PR96 合入后的评审指出，新增的独立 helper 场景也计入同一增量的测试上限；仅按注册的
测试函数计数不正确。后续修正移除重复的永久场景，保留冲突、重放和并发的关键回归；
此前真实库与跨版本消费者的运行记录继续保留，不以合并或删减测试改写既有结果。

## 原生历史检索 child 与 S0 重投影（2026-10-27）

已安装的 `history.query/v1` 是一个只读 native child，用 `[delegate:history.query:1]` 调用：
`op=search` 检索已提交的原始事件（中文及混合中文走 LIKE，其余优先 FTS5、异常回退 LIKE），`op=list`
按 seq 列事件，`op=read` 只接受一个 `event_id` 或 `seq` 返回原始 `data`。返回按 seq 升序，
`search/list` 只给最多 400 个 Unicode 标量的 `data_preview`，完整正文必须显式重读；
搜索对能定位的字面匹配提供附近正文，不能定位的 FTS 归一化匹配保留前缀且标记匹配未显示。
`data_preview_start_char` 是原始 `data` 中 Unicode 标量偏移，附两侧截断和匹配可见标志；
预览中没有某项不代表原文没有。输入 `deny_unknown_fields`，`limit` 有界。冻结输入在 CAS 里，
重试解析原 operation，不重新派发第二次读取；未返回的回忆不得当成已核实事实。

搜索预览行为变更同时改变 native handler 的 artifact digest；已绑定旧实现且尚未终态的 task
不能静默改绑，需恢复原实现或按既有恢复合同显式对账。查询不会因此重复派发。

投影与封印之间的并发也修了：S0 之后如果原始历史又追加了事实，或执行类提交改变了某个调用
的状态（raw leaf 不变），现在返回 `ResnapshotRequired` 并基于新事实重新投影同一 planned
step；不再让主体停在半途，也不会把已发出的请求当成可重放。这正是保留数据集在第 4 步
停止的原因，修复后同一数据继续提交。

实测（`docs/evidence/c09-native-history-replay-20261027.json`）：合并 main 后受影响 cargo
目标 0 failed；用真实二进制在保留数据的绑定路径上重放 80 秒，原第 4 步封印成功并连续提交
到第 298 步、306 条原始事件，S0 冲突 0 次；期间真实执行的 `history.query` 任务 3 个全部
terminal，其中 `{"op":"search","query":"深刻","from_seq":0,"limit":5}` 在 306 条事件里
按 seq 升序返回 5 条（1,3,4,5,6），只带有界 preview。provider 是脚本 fixture，因此这不是
模型行为证据，也没有驱动 Web UI。
