本轮（feat/c11-durable-input-20261029）实现 §41.18 durable append 接纳与恢复切片；源码已写，父协调者尚须运行下述验证，不能据此声称实机或浏览器已通过：

- `Store::admit_web_submission` 在同一 ledger 事务提交原始 InboxEvent、submission 绑定和 admission commit，再回复 accepted。同 subject 下相同 submission_id + payload 重放原 event_id/commit；不同 payload 返回 conflict，不改写原事实。正文不能自报另一个 subject。
- accepted 回执不等待模型、暂停解除或 mpsc 容量。`try_send` 只提供非阻塞唤醒/副本；正常 Planned 步骤按剩余 64-event 上限直接读取持久 pending 行，与 volatile 副本按 event_id 合并，以持久原文为准。深于 1024-slot 的 backlog 不再启动时灌入自己的 channel，因而没有自等待；未唤醒输入仍由后继步骤读取。
- `inbox_events.consumed` 仅标记已在 `stage_subject_inputs` 事务中保存为 Planned 步骤的恢复资料，不是 selected。共享恢复通道 `pending_inbox_events` 覆盖 source `web_ui`、`playground` 与 `media/{provider}` 的完整 InboxEvent 原始行（消费标记同一 staging 事务完成）；native-child 的 task_result 仍走既有 T2 路径。selected 必须找到非 Planned 的实际 step，并校验其不可变 `input_plan_ref` 的 CAS 长度/digest、schema/step 身份、原始 event 及 raw-event 身份成员关系。`prepare_context` 在投影前逐条核对 fresh raw ID，S0 Store 校验把这个集合封口；预算/CAS/resnapshot 失败的 staging 不冒充选入。
- `query_submission` 读取 accepted、真实 sealed selection 和 `event_disposition_commit` 的 S1 处置；无持久记录才是 not_admitted，读取失败是 temporarily_unavailable。写入错误/closed writer 先走只读查询：已有同 payload 回放原 accepted，冲突保持 conflict；只读也失败则 unavailable/unknown，不把丢 ACK 的已接纳输入说成拒绝。
- 正式 Proto-UI controller 在发送前把每条提交的 submission_id 与精确 payload 存到独立键 `shenko.submission.v2.<submission_id>`；保存失败不发送。每条记录自己的键避免多 tab 整数组覆盖彼此未确认 ID；重开时逐个恢复，不自动换 key 再发送。committed、conflict、rejected、not_admitted 等终态事实会退休该 pending 持久记录（UI 历史不是 durable outbox，终态事实已存于服务端 ledger）。每次发送递增 client 侧 `send_epoch`，query_submission 携带并由服务端原样回显；视图 epoch 小于当前尝试的旧 not_admitted 不恢复草稿、也不降级更新回执已给出的事实——真正未接纳且属最新尝试的 not_admitted 仍允许同 ID 重发并恢复用户输入。在线有 unresolved 回执时每 2 秒发真实 Store 查询，故不断线也能观察 selected/committed；与 timeline 输出无推断关联。草稿和阅读状态不因回执更新而重置，现有 keyed renderer 的选区/锚点机制未替换。显式 conflict 行不被重开后的普通查询冒充为原内容已接纳。
- Proto-UI pin 仍是 `7181a93a5ec5cad43936a72e31d5477d5488733a`，上游 lock SHA-256 `3ac437fda5666f744c02587d9c90b47a927a6e2521973f6a18b47cc3c7cbe422`，本切片没有更新 pin、compiler 业务、Cargo/pnpm 依赖或 lockfile。`src/static/` 生成资产没有手改，父协调者使用既有 `build.mjs` 一次重建。

本切片不实现 withdraw UI、live steer、完整 PresentationReceipt 历史明细或跨节点 Web admission 归档恢复；steer 继续如实不可用。新增永久 consumer 场景按独立行为保守计为 8：full/paused inbox 接纳、closed-writer 丢 ACK 重放、同 key 冲突、Planned staging 非 selection、真实 S0 selection、1025-row backlog 恢复、在线回执/草稿/阅读保持、页面重开同 ID 对账。此前 store test 内的 pending/lookup/手工 consumed 等独立小场景已移除，不以函数或 helper 分组规避上限。

### 父协调者可运行的原生／浏览器 recipe（本 worker 未运行）

1. 在受管 devcontainer 内持共享 heavy-work lock，串行运行受影响 Rust suite（`shenko-store`、`shenko-subject`、`shenko-ui`）。`web/` 内运行 `pnpm check`、`pnpm test`；后者只是确定性 controller/transport fixtures，不是浏览器、真实 Store 或 provider 验收。按现有 `PROTO_UI_SOURCE` pin 调用 `pnpm build` 一次生成正式资产。
2. 使用隔离持久 `SHENKO_DATA_DIR`、父协调者确认的真实 provider/profile 和已构建二进制：`shenko --data-dir "$SHENKO_DATA_DIR" start --port 7860`。不得用 offline broker 或另一条聊天主体代替真实循环。记录 `/api/self` 的实际 subject_id、初始 head、provider 绑定和服务版本；不可把 configured 当作已调用模型。
3. 从正式首页 append；保留 WebSocket submit 原 JSON 和 localStorage `shenko.submission.v2.<id>` 键。丢弃第一次 receipt 再断连/重开页面；只观察同 key 的 query/retry 与原 event_id/accepted_commit；两个 tab 并发 append 时检查未确认键互不覆盖；终态（committed/conflict/rejected/not_admitted）后该键应消失。让真实 subject 继续运行，保留连续连接中从 Store 查询得到的 selected、S1 committed 及对应 sealed plan/disposition。对同 key 同 payload 再发不应新增 inbox/input；对同 key 改内容及不同 subject 应拒绝且原文不变。
4. 用实际 `runtime pause --request-id <稳定UUID>` / `runtime status <UUID>` 等到 Paused；填满 live inbox 后再 append，accepted 与同连接查询不应阻塞。`runtime resume <UUID>` 后观察 pending 被真实 S0/S1 消费；另在重开前形成 1025 条独立持久输入，重开同 data_dir 后按有界步骤接续，不能卡在第 1025 次 channel send。
5. writer closed / 原 ACK 丢失路径应重查原 durable row；可查时重放 accepted，读也不可用时保持 unknown 和原 ID，不能恢复成“明确未接纳”的新草稿。阅读历史时选择一段已有正文、保持新草稿和锚点，让查询回执及新的 committed replay 更新；记录选区/锚点/草稿不被替换及稳定 part 身份不重复的浏览器证据。以上是待执行 recipe，不是已通过声明。
