## 当前已具备与真实差距
kernel 只使用固定上游 rev `1754062cef67cfc119fc7a2084c0321a231b9092` 的原生合同：
`Supervisor::spawn<P: cordis_core::Plugin>(plugin, config)` → `Plugin::prepare` →
`PreparedPlugin::from_input` → `Context::spawn`。返回真实 `FiberHandle`，供
`Supervisor::restart(&fiber)` 进入同一 Fiber 的原生换代；`Context::provide<S: Service>`、
`InjectSpec`、`Context::run/effect/effect_sync` 建立实际依赖和 generation-owned 清理。
旧候选 ec5d446 的作者/提交和原现场保持不变；当前增量向前删除旧 Shenko Plugin trait、
meta/start/stop fallback、PluginContext/generation 计数、字符串 PluginService 和独立 ServiceRegistry，
不提供双路径或旧字段别名。所有仓库内旧接口调用者（两项 kernel 测试）已迁移，其他业务调用不冒充已接入。

Why：采用 Cordis 自己的 typed allocation residency、panic containment、递归拒绝及终止 barrier，
不再用一个串行命令队列包裹生命周期。Shenko 仅负责 terminal admission、创建等待者取消后的完成所有权，
以及 attempt-all typed shutdown。短 admission 锁不跨 await；completion 使用 `Context::spawn_attributed`
保留上游 settle attribution。stop 封闭 admission、取消未完成 spawn，并经真实
`Context::remove_plugins::<P>` 等待清理/unlink；重复或回调内 concurrent stop 明确返回 in-progress 错误，
不能把该错误当清理完成，稍后可再 stop 取得 barrier。Native cleanup 的 stop signal 由插件在
`Context::run` 的 join 登记之后注册，遵循 LIFO；不存在一个过早注册的兼容 stop。

Cordis 的 drain 失败只通过 logger 报告，不等于 `dispose/remove` 返回错误。kernel 保存已归一化的
原生 `LogRecord`，对 pinned `cordis:` warning/error 闭锁后续 admission/restart，stop 仍尝试全部 allocation；
读取错误不会清除 unknown。任意 error Display 与 panic payload 的异常销毁由真实上游 containment 处理，
本层不再调用这些对象。该诊断绑定固定上游日志合同，不是耐久外部效果对账服务；手动 effect dispose
直接返回的失败仍由调用插件处理。换 runtime、进程被杀或机器断电也不证明外部效果已撤销。
正常退出仍必须 await stop；此切片不提供任意 Runtime Drop 后的自动业务恢复。

定向证据：在容器磁盘候选 `/tmp/shenko-c03-native-20261025` 上，
`cargo test -p shenko-kernel` exit 0：改写原两项兼容测试为真实 native Service/InjectSpec/effect
场景，仅新增一项 pending-start shutdown 回归（共三项）。覆盖 typed Pending→Active、真实同-Fiber restart
与 Service publication occurrence 更换、run signal/join、cleanup 回调重入、声明 panic 不丢健康 Fiber、
失败 apply 隔离、error Display 与 panic payload destructor 均 panic 时继续清理且 unknown 不清除，
以及调用者取消/未完成 apply 在 stop 后不再创建 effects。它们是 kernel/库集成证据，
不是 A18/H08 或完整 C03 验收通过；不沿用 ec5d446 的旧测试结果为新实现背书。

**仍有生产装配缺口**：当前 `bin/shenko` 仍直接构建业务服务，未安装默认 Supervisor 插件闭包；
本切片不改 #6 恢复线的 main/subject/store/broker/SSH，不声称默认业务闭包已经 cordis 托管。
下一切片须与 #6 在 issue 评论协调装配 owner，移除对应直接构造路径而非重复启动同一业务服务。

在途闭包租约与 §41.12 durable activation/handoff 仍欠。restart 是破坏性换代，不是原子热图发布。
