## 2026-10-29 seat 身份与受守卫写入切片（不是 C07 完成）

- base：main `5959e455af637fd1edd55fbeb2e94af725131b74`；改动只在 `crates/shenko-exec-ssh`（`src/ssh_exec.rs`、`README.md`）。无 store/schema/协议变更，无信任假设变化。
- `TmuxPane` 增加 `pane_pid`/`dead`（serde default 兼容旧数据；旧 tmux 缺列按 0/false）。`list_panes`/`capture_pane` 共用一份 11 列格式，`capture_pane` 不再用重复手工解析。
- `discover_agent_seats` 改为返回 `AgentSeat { pane, kind, processes }`：对每条 pane 用 `ps -axo pid=,ppid=,args=` 从 `pane_pid` 收集进程子树，跳过 shell/tmux/sudo 等 wrapper，按首个非 wrapper argv 归类 `claude`/`omp`/`codex` → `SeatKind`、其余 → `Other(comm)`；裸 shell 与 dead pane 不再是 seat。`ps` 不可用时退化到 `pane_current_command` 且 `processes` 为空（未核验证据）。旧实现按 pane_current_command 子串匹配，会把 bash/zsh 当 seat、也无法区分 adapter——已替换。
- `send_keys_verified`/`send_input_verified`：单条远端命令内先查 pane 存在、非 `pane_dead`、`pane_current_command == expected_command`，再 `send-keys`；拒绝映射为可下转的 `SeatRefusal`（`PaneMissing`/`PaneDead`/`ProgramChanged`），普通失败仍是 `ExecFailure`。这覆盖验收「旧问题/退回shell不被盲输」的入口防线，但 tmux 无原子 check-then-send，检查与发送之间仍有竞态窗口——拒绝盲输，不是送达证明。
- `SeatObservation` 增加 `screen_hash`（纯文本画面 digest），供回答前比对画面/问题 revision。
- 新增 2 个测试场景（独立计数 = 2 ≤ 9）：进程子树解析/归类；受守卫命令构造 + pane 行解析 + 拒绝码映射。未改既有 13 tests。
- 建议父验证命令：`CARGO_BUILD_JOBS=1 cargo test -p shenko-exec-ssh`；`cargo build -p shenko-exec-ssh --example task_ssh`；如有 loopback tmux/ssh 环境可对 `TmuxSeat::local` 实测 `list_panes`/`discover_agent_seats`/`send_input_verified`（死 pane 应返回 `SeatRefusal::PaneDead`）。
- 仍缺：持久 TaskSeat/lease 记录与单写者仲裁（C08 候选在 shenko-store 推进）、question revision 绑定到 DecisionRequest、结构化 RPC/SDK 接 Claude/OMP、`screen_hash` 与实际 question 生命周期接线、公钥 UI（R017）、keygen（R016）、WASM SSH（C06）、真实 Claude/OMP journey 实测。`SeatKind` 只识别 argv 可见的适配器；包装在 node/bun 内运行的 CLI 会归为 `Other`。

## 相对 CAS 根上的已封存 SSH 信任（2026-10-28）

产品 source `267fcb5ca7c1d8c07821dcb8a31f00f2b09c7082` 修复一个已真实复现的 native adapter
可用性缺陷：`Store::open` 接受相对 CAS 根，但在 T1 后，`SshBinding` 原样把相对 known_hosts 路径
交给要求绝对路径的 OpenSSH 执行器；因此真实 transport 未启动，原 attempt 保持 unknown，query 也
因同一问题无法到达原 remote receipt。修复先核验当前 CAS 中的 trust 对象，再取其绝对路径；不使用
历史 locator、系统 host-key fallback 或重发原 armed 请求。

使用全新隔离 loopback sshd、一次性测试 key 和各自全新 SQLite/CAS 的真实 OpenSSH consumer，先确认
握手及 host pin 可用：修复前 transport 为 None、远端 marker 0、原 operation reconciling/单 attempt
unknown；修复后新 operation 有 completed receipt、marker 恰好 1 次，同一 operation 的 query 读回
原 receipt 且 attempt 仍只有 1 个，错误 host pin 被拒并未产生额外 marker。任意 exec 的业务效果仍为
unknown，因此 operation 仍 reconciling；不把进程成功冒称业务完成。

source `267fcb5` 的 3 个 SSH tests 和真实 example build 通过。前后实机隔离结果、工具/二进制 SHA 与
