### NapCat ingress 高位无符号身份修复（局部候选）

- OneBot `message_id` 是非零整数时，接收库按完整 `i64::MIN..=u64::MAX` 范围生成来源身份；同一十进制字符串与整数沿用原有等价规则。原有非零字符串、数字／字符串零、浮点数及缺失会话信息的处理不变，无法确立身份的事件仍为弱去重。身份仍按 NapCat 账号、会话及协议域区分；修订和内容冲突仍是不可执行观察。
- 接收库 schema v3 在同一个 SQLite 即时事务中迁移 v1/v2：高位无符号旧事件重新绑定来源键，与已有字符串来源合并；原事件的 seq、spool ID、dedup key、weak 标记、raw、接收及交付时间、consumed 和 disposition 原样保留。所有旧观察的原 key、raw hash、body 和历史 event ID 保留，通过独立 canonical key 查询；即使不同旧来源各有相同 raw 的观察，也不会合并删除。重放根据新来源键去重，新的修订／冲突作为观察保存。
- `identity_reconciliation` 按原 seq 列出受影响事件、最早来源事件和基于该事件的 original／metadata-only／conflict／revision 分类。只有一个旧事件的组保留其原 delivery eligibility。若多个旧 spool ID 现归为同一身份，先将**整组**从 pending 投递中隔离：旧代码先向 channel 发送再写 `delivered_at`，所以空时间戳也不能证明其它 ID 未被投递；不能把第一条当成确定未投递或把后续记录伪造为已 ACK。既有消耗和处置保持不变，原始事件及观察仍可查询。
- `reconciliation_status` 保留逐事件未知状态和持久类型化证据。运行时分页查询当前主体分支控制账本的实际非 deferred S1，`reconcile_from_store` 记录真实 commit 引用；缺少 S1 不能证明未投递，也不能排除其它分区或分支事实。有真实 S1 的组继续阻止新投递，同时保留其它尚不确定的事件；历史本地 ACK 与真实 S1 矛盾或已验证的未投递证明与后续事实矛盾时，显式标为 `contradictory_evidence` 并重新隔离。它们不会改写旧 raw、观察、consumed 或 disposition。
- `submit_never_dispatched` 为后续证据提供真实接口：证据绑定 ingress cursor、账号、主体、控制 ledger、原始／后续事件 ID、seq、raw hash 和 sealed proof；调用方必须提供实际可信 verifier，验证证明内容、来源和全部旧 writer／consumer epoch 的持久 fencing，证明该后续事件既未投递也不会迟到。仅当**所有后续事件**均有该证明、没有冲突或已提交处置且原事件未消费时，事务才释放原始 spool ID；迁移前原事件已有 eligibility hold 时保留 `prior_eligibility_hold`，重复记录不可执行。释放记录与证明、eligibility 同事务持久化，交付循环能处理早于当前扫描水位的新释放，并在 channel send 前于 SQLite 写锁内复核资格。释放只在绑定了相同主体及控制 ledger 的 handle 可见；正常运行时自动绑定，不需人工许可。
- 未决边界：旧协议没有 dispatch-before-send 记账或完整的旧 owner fencing 证明，缺失 S1／`delivered_at` 不能构造未投递证明；当前仓库没有可为这些历史事件签发该证明的生产 verifier。因此缺少权威证据的组继续可查询地停留在 `awaiting_evidence`，以后真实证据到达可调用上述接口；不会伪造“从未投递”以清空隔离。升级前必须停止所有旧版 spool writer／delivery loop 并对账在途任务；SQLite 事务无法撤销已经排出的消息，也无法阻止已打开的旧版进程在事务后继续写。缺失身份字段、超出受支持整数范围或已转成浮点且丢失精度的输入无法据此推造身份。旧弱 key 不是该事件独有的真实 spool key、事件主体与存储列矛盾、来源组或旧观察无法绑定同一身份等情况会拒绝迁移并回滚；须检查真实数据，不自动猜测修复。此处为代码与回归测试候选，尚不声称已运行测试、真实 QQ 验收或完整 C13。
