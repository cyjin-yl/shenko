# 文档体系合同

本文是文档层的功能合同：它规定文档**怎么分层、谁拥有哪一层、导航如何保持真实、错误如何被发现与恢复**。它不是任务列表，也不是进度板。

## 目的

Shenko 的文档要同时满足两件互相拉扯的事：规格必须不可变地保存用户原话与验收分母；现行说明必须能被今天接手的人直接使用。2026-11-01 之前，两者挤在同一层——根目录的 `GOAL.md`、`PROMPT.md`、`HANDOFF.md` 既是"当前指令"又是"历史来源"，`docs/tasks/` 里的 22 张任务卡既是任务定义又是进度板。结果是旧环境约束（"最多 5 条 workflow"）继续被当作现行规则读，而真正的事实来源（源码、SPEC、证据）反而埋在下面。

分层的目标是让"当前该读什么"成为唯一且机械可判定的问题。

## 分层

| 层 | 内容 | 可变性 |
| --- | --- | --- |
| 规格层 | 根目录 `SPEC.md`（§1–47 + §48） | §1–47 与全部用户原话**字节不可变**；§48 是唯一允许的追加章节 |
| 功能合同层 | `docs/specs/architecture.md` 与 `docs/specs/<domain>.md` | 由各领域代码拥有者维护，写稳定的功能、接口、理由、错误与恢复合同 |
| 治理层 | `docs/governance/` | 自主边界、交付合同、许可、接续与协作规则 |
| 索引层 | `docs/INDEX.md`、`docs/IMPLEMENTATION_DOCS_MAP.md`、`docs/domain-specs.json` | 导航与状态描述，必须与实际文件一致 |
| 追踪层 | `docs/requirements/`、`docs/state/coverage.json` | 与 SPEC 同源的机器可读分母与逐项状态 |
| 证据层 | `docs/evidence/` | 真实运行的候选、环境、方法、结果与边界 |
| 历史层 | `docs/history/`、`docs/research/archive/` | 只保留来源与字节，不是现行指令 |

### 不可变前缀

`SPEC.md` 的前 783,140 字节是 §1–47 与 U01–U63 的原始内容，SHA-256 为 `594edc2e5a282cf9cf51812bda0a05e988ea16a68af007962cf4e9de0123c077`。追加内容必须以 `# 48 ` 标题开头。这条约束记录在 `docs/history/spec-integrity.json`，由 `scripts/check_docs.py` 逐字节校验。

### 归档而不是删除

`/tank` 不允许文件删除，因此"撤下"一律实现为**移出 + 保留原件字节**：

- 原 `GOAL.md`、`PROMPT.md`、`HANDOFF.md` → `docs/history/entrypoints-20261101/`；
- 旧进度板、交接稿、goal 状态快照、旧计划与编制期治理草案 → `docs/history/progress-20261101/`；
- 22 张社区任务卡 → `docs/history/task-cards-20261101/`。

`docs/history/archives-20261101.json` 记录每个文件的原路径、归档路径、SHA-256、字节数与归档理由，并断言它们与基线提交 `78f5f63` 逐字节相同。根目录不保留兼容入口，也不新增符号链接；唯一的符号链接例外是既有的 `CLAUDE.md → AGENTS.md`，它继续指向同一份开发规则。

### 历史链接的解释

§1–47 原文中指向旧 `GOAL.md` 等路径的链接属于旧文档布局，按 §48.5 解释：链接保留原样（不改原文字节），`scripts/check_docs.py` 在校验链接时把这些目标解析到归档清单，并要求归档原件确实存在。历史文档里的链接因此既不会因为"文件搬走了"而误报，也不会因为"把 SPEC 改干净"而丢失来源。

## 所有权与注册

`docs/domain-specs.json` 是领域合同的登记表：每条记录给出文件路径、拥有者、当前负责的 Agent 与覆盖的 SPEC 章节。新增或改名一条领域合同必须同时更新这个登记表，否则校验会报"未注册的领域合同文件"。

各领域合同由该领域的代码拥有者撰写，内容是稳定合同，不是任务列表或进度：

- 写**功能**：这个能力做什么、边界在哪；
- 写**接口**：类型、调用路径、生命周期；
- 写**理由**：为什么这样分层或不这样分层；
- 写**错误与恢复**：失败时留下什么事实、如何重新取得控制。

不写"谁在什么时候做完第几步"。

## 导航

`docs/INDEX.md` 是唯一的导航入口，回答三个问题：现在该读哪份文档、这份文档归谁、它现在是什么状态。状态词只有事实性的几类——**已接线**（在 `bin/shenko` 装配路径上有实际调用点）、**仅源码**（有实现与类型但无调用点）、**未实现**（仓库里没有对应实现）——并且只在 `docs/IMPLEMENTATION_DOCS_MAP.md` 中使用。README 只做产品介绍、安装、使用、扩展与导航，不承载状态判断。

`docs/IMPLEMENTATION_DOCS_MAP.md` 的每条状态都必须能在源码里复核：要么给出调用点，要么说明缺哪个调用点。它描述源码事实，不构成运行验收。

## 校验

`python3 scripts/check_docs.py` 是文档层的可执行检查。它验证：

1. `requirements.json` / `behaviors.json` / `sources.json` / `acceptance-cases.json` 的编号与来源行与 SPEC 一致；
2. coverage 账本覆盖全部 147 项需求，且每项"已满足"都有证据引用；
3. 历史 v0.5.1 快照与 46 份归档稿的 SHA-256 未变，U01–U49 逐字保留；
4. `SPEC.md` 的不可变前缀字节未变，追加内容只允许 §48；
5. 2026-11-01 归档清单中的每个文件存在、哈希与字节数相符，且旧位置不再存在文件或符号链接；
6. `docs/specs/` 中的每个文件都已注册，且每条登记记录指向存在的文件或明确标记为待交付；
7. 必读 Skill 组存在、frontmatter 合法、`.claude/skills` 与 `.codex/skills` 符号链接指向同一规范源，`CLAUDE.md → AGENTS.md` 成立；
8. 全部本地链接可解析（历史文档与 §1–47 的旧链接按上文规则解释）。

它**不**验证产品行为、构建结果、模型能力或任何验收场景；输出里的 `product_tested` 恒为 `false`。真实验收由产品实现提供。

## 错误与恢复

| 情形 | 表现 | 处理 |
| --- | --- | --- |
| 链接指向已归档文件 | 校验报"Broken local link" | 把链接改到归档路径，或按 §48.5 保留旧链接并登记归档清单 |
| 领域合同尚未交付 | 校验列出 `domain_specs_pending`，不报错 | 由该领域的代码拥有者交付；导航与登记表先行更新 |
| 出现未登记的 `docs/specs/*.md` | 校验报"Unregistered domain spec file" | 登记进 `docs/domain-specs.json`，或删除多余文件 |
| SPEC 前缀被改动 | 校验报"SPEC.md original prefix changed" | 从基线恢复前缀字节；只允许在末尾追加 §48 风格章节 |
| 归档文件被改动 | 校验报"Archived file changed" | 从基线提交恢复原件字节 |
| 旧路径复活 | 校验报"Retired path still present" | 移回归档位置；不要在旧位置留兼容入口或符号链接 |

## 为什么这样分层

- **不可变规格 + 可变说明**：用户原话与验收分母是外部承诺，改动它们需要新的用户裁决，不属于实现自由。说明、导航与状态则必须随实现变化，否则读者会按过期信息行动。
- **归档而不是删除**：删除会丢失"为什么当初这么写"的来源，也会让已发出的引用指向虚空。保留字节并标注历史身份，既保住来源又消除误读风险。
- **机械可判定**：编号一致性、原文字节、归档哈希、链接与符号链接都能机械检查，不依赖任何人记得规则。"当前该读什么"因此不需要靠阅读顺序或口口相传传达。
- **状态词只有事实来源**：把"已接线 / 仅源码 / 未实现"与"已验收"分开，是因为源码存在与真实运行是不同证据层；文档层不生产运行证据，只如实描述源码并指向证据目录。
