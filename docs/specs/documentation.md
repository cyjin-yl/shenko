# 文档体系合同

**内核定位。** 本文是方法合同，规定文档体系，不属于运行时内核。运行时的不变量见[内核合同](kernel.md)。

## 为什么开发规范采用高自主、强证据

本项目的瓶颈不应是人类逐项许可。开发 Agent 可以自行选择实现、修改计划、并行委派、修复失败、更新依赖、打开与更新 PR。它仍需分清目标完成、代码存在、模拟通过和真实运行通过。否则“很自主”会变成更快地宣布假完成。见 [§40](../governance/development-contract.md#spec-40)、[§46](../governance/COMPLETION.md#spec-46)，以及 [开发治理研究](../research/agent-development-governance.md)。

所有开发者先读 [shenko-dev](../../.agents/skills/shenko-dev/SKILL.md)，再按实际需要组合八个原子开发 Skill。验证用于消除真实疑问，可以复用已有证据，小改动可以零新增测试；一个连贯增量不得新写十个或更多测试，也不能换一种拆分方式绕过。充分验证后继续交付，不让测试数量和审批步骤替代功能进展。Rust 实现明确使用 2024 edition，`CLAUDE.md` 通过符号链接共用 `AGENTS.md`。见 U55/U58–U59。

完整产品是唯一范围，S1–S5 只是工作顺序；首版自开发闭环提供后续演进能力。执行者在自己的 fork 自主开发、合并、重构、配置工具和 CI，可以同时运行大量实现 agent。验证帮助它发现和修复坏候选，一个 PR 等待 review 时照常整合后续工作。完整且有证据的 ready PR 是交付结果，上游拥有者随后处理合入。见 U50–U51。

## 为什么这些规矩也能演进

规则保留意图、前提和可观察效果，方法可以更换。模型变强、工具改变、论文被推翻或部署不同，都应促成更合适的实现。开发 Agent 可以更新自己的说明和 harness；只有新的真实用户决定可以改变用户目标，只有新的执行证据可以改变已发生事实。理解这种区别，比积累更多禁令更有用。

本文是用户要求与 SPEC 合同的说明性导航，不新增隐藏产品范围或独立人类 gate。每段关联的 U/Ref 及上游采用范围可在 [§31](../requirements/research-sources.md#spec-31)–[§33](../requirements/user-sources.md#spec-33)、[§39](../requirements/design-provenance.md#spec-39) 与 [来源索引](../requirements/sources.json) 查到。功能合同在 [docs/specs/](.)，文档导航在 [docs/INDEX.md](../INDEX.md)。

本文规定文档的权威关系、来源保全、导航和校验。它不是任务列表或进度板。

## 目的与 Why

接手者应能直接找到某个行为的完整合同和理由，而不必读完一份巨型规格，再猜哪些补充已经覆盖旧句。按领域拆分，让功能、接口、Why、错误与恢复放在一起；保留原话、编号和历史原件，让整理文档不变成改写事实。

2026-11-11 的拥有者决定取代旧的根文件布局：`SPEC.md` 和 `WHY.md` 的正文全部拆入 `docs/`，根文件仅留导航。现行权威不能退回根文件，也不能在 `docs/` 中再复制一份同样的巨型主文件。实现者从意图、前提与可观察效果推导方法；方法可以变，用户目标和已经发生的事实不能被实现便利悄悄改掉。

## 分层与权威

| 层 | 内容 | 维护边界 |
| --- | --- | --- |
| 领域合同 | `docs/specs/` 以及索引指向的专题合同 | 维护功能、接口、Why、适用前提、效果和恢复语义；最新明确用户决定控制意图 |
| 来源与追踪 | `docs/requirements/` | 保存用户原话、R/B/Ref/case 身份及实际文档位置，不靠旧根路径间接定位 |
| 治理 | `docs/governance/` | 自主边界、完整交付合同、许可、接续与协作规则 |
| 导航 | `docs/INDEX.md`、`docs/IMPLEMENTATION_DOCS_MAP.md`、`docs/domain-specs.json` | 按真实文件与源码维护入口、归属和状态 |
| 证据与状态 | `docs/evidence/`、`docs/state/coverage.json` | 记录候选、环境、方法、实际结果和剩余缺口；文档迁移不提高验收等级 |
| 历史 | `docs/history/`、`docs/research/archive/` | 保留原件字节和出处，不作为现行指令 |
| 根入口 | `SPEC.md`、`WHY.md` | 只引导到当前文档，不重复正文、不再接受规格追加 |

## 来源保全与迁移

[迁移映射](../contract-migration.json) 记录原件、来源提交、哈希、旧章节及当前目标。旧章节编号是可追溯标识，不再意味着读者应回到根文件查正文。

迁移必须满足：

- 原件有完整快照、字节数与哈希；迁移块完整覆盖来源，没有遗漏或重复认领。
- U 原话逐字保留，R/B/Ref/case 标识和验收义务不因拆分丢失。原话中的旧称呼是历史事实，不擅自润色。
- 机器索引采用 schema 2，每项 `source_path`、`source_markdown_line`、`source_row` 指向实际新文档；旧位置保留为迁移来源，不冒充当前定位。
- 现行引用直接指向具体文档和锚点。遇到“完整合同见旧章节”的句子，迁移完整合同并改引用，不能只给索引首页。
- 源码注释、开发 Skill、种子单元、脚本与机器索引中的旧入口也在维护范围内。保留历史记录的例外必须明确，不能成为现行失效引用的通用豁免。

旧 `docs/history/spec-integrity.json` 的不可变前缀约束用于验证归档原件，不限制当前合同的合理修订。需要改变产品目标时记录新的真实用户决定；一般说明、布局、链接和方法应直接修订当前文档，不再通过无止境追加根文件章节维持两套读法。

### 既有归档

原 `GOAL.md`、`PROMPT.md`、`HANDOFF.md` 已进入 `docs/history/entrypoints-20261101/`；旧进度板、交接稿与计划进入 `docs/history/progress-20261101/`；22 张社区任务卡进入 `docs/history/task-cards-20261101/`。其清单、哈希与字节数由 [既有归档清单](../history/archives-20261101.json) 保留。

## 所有权与内容

[领域登记表](../domain-specs.json) 登记 30 份领域合同的文件、拥有者和覆盖范围。新增、改名或合并领域合同要同步登记，不能留下两个互相竞争的权威来源。

领域拥有者维护稳定合同：它做什么、为何存在、适用条件、如何观察到效果、接口、失败后留下什么事实和怎样恢复。实现方法可替换时明确边界，避免把当前模型的补丁写成永久产品公理。日常进度留在 Issue、PR 与交接记录，不写成合同。

## 导航与状态

[INDEX.md](../INDEX.md) 是起点，按领域和问题引导到具体内容；[实现地图](../IMPLEMENTATION_DOCS_MAP.md) 说明源码中已经接线、仅有源码或尚未实现的部分。每项实现判断要能回到实际调用点或明确缺口。

README 介绍产品、安装、使用和扩展，不再重复易过期的完整规格表。引用中确需分母时从机器索引核对；本次迁移基线为 165 项需求、63 组行为、59 条来源、236 条具名验收。后续变化以实际索引和来源为准，不把这些数字当成固定目标。

源码存在、文档齐全和真实运行通过是不同事实。状态地图不能把“已接线”换成“已验收”，文档迁移也不能把覆盖账本中的未验证改成满足。

## 文档完整性校验

`python3 scripts/check_docs.py` 只检查文档完整性：

1. 需求、行为、来源和验收编号与当前合同一致；索引绑定的文件、行号和来源行真实存在。
2. coverage 保留全部需求，引用的验收项存在，已满足项有证据引用。
3. 历史快照和归档文件的哈希、字节数不变，原始用户话语保留。
4. 迁移清单中的原件、块覆盖和目标可验证，根入口只作导航。
5. 退役入口未复活，领域文件已登记，开发 Skill 与共享入口的符号链接完整。
6. 现行本地链接及锚点能指向实际内容；历史材料按明确的来源保全规则处理。

检查的 `product_tested` 为 `false`。它不能证明构建、模型能力、运行场景或自升级已经通过，真实运行证据仍由产品验证提供。

## 错误与恢复

| 情形 | 处理 |
| --- | --- |
| 现行链接仍指根 SPEC/WHY 正文 | 依据迁移映射改为实际领域文档和锚点；缺少正文时补齐迁移，不用索引跳转掩盖 |
| 索引来源行不匹配 | 核对当前正文，更新实际路径、行号和来源行；保留旧定位及原件 |
| 迁移块缺失或重复 | 对照已保全原件恢复完整内容和单一归属，不能删掉验收项使检查通过 |
| 归档文件变化 | 从记录的来源提交恢复原件字节，不把现行修改回写历史 |
| 未登记领域文件或失效目标 | 补充归属或纠正目标，同步导航，保留已有作者与历史 |
| 旧任务入口复活 | 恢复既有退役布局；不新增旧入口的兼容副本 |

## 可变通的边界

文档格式、组织和校验方法可以随实际需要调整。不可变的是对真实来源与结果的诚实：保存用户原话，不丢未完成义务，不伪造验收，不让过期导航成为第二套产品规则。这样既允许 Agent 从 Why 变通，也让接手者能核对每次变通保留了什么。

## 现行合同消费

`docs/contracts.json` 是现行文档清单。证据索引和自我知识从清单读取当前全文；`docs/contract-migration.json` 只用于迁移保全审计。新增 R/B/验收项无论在旧迁移标记内外都必须被计入，并同步需求机器索引；新增领域文档必须加入清单。新条目无需旧源码行或迁移来源。

普通 `scripts/check_docs.py` 检查现行全文与索引，并保全原始归档。一次性迁移 checkpoint 额外使用 `--verify-migration` 校验搬迁时块摘要；此模式不是未来修改合同的冻结门槛。原始用户原话仍不得改写。
