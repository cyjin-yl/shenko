# 内核合同：九条不变量与参考插件的边界

本文规定什么属于 Shenko 的内核，什么是默认安装、可以替换的参考插件。来源与采纳过程见[决策 0007](../decisions/0007-kernel-and-reference-plugins-2026-11-11.md)。代码怎样一步步向本文收敛，见[内核收敛计划](../development/kernel-convergence.md)。

这是目标行为合同。每一条末尾的“当前实现”如实标注代码今天做到哪里；合同写下来不等于已经实现，源码存在也不等于运行验收。本文不删减任何既有需求、行为或验收：165 项需求仍由各领域合同承担，本文只回答“它们当中哪些是地基，哪些是可以换的家具”。

## 判据

一条规则留在内核，必须同时满足两点：

1. 没有它，别的部分就不能被安全地替换。
2. 它只检查结构，不判断意思。

不满足的规则属于某个可安装单元，也就是参考插件。参考插件依然重要，依然默认安装，依然承担各自的需求；区别只在于它带着自己的 Why，实现它的 agent 可以按所处环境改写或替换它。

内核因此只有一个任务：让其余一切都能被换掉，而主体还活着。

## 三个问题

九条不需要逐条背诵，它们是三个问题的答案。

## 每一条怎么读

每条先给合同正文，再给六栏 Why，最后是当前实现。

- **意图**：这条要保住什么。
- **前提**：它在什么条件下才有意义。
- **可观察效果**：怎样从外部看出它成立。
- **灵活边界**：实现者可以改什么，不能改什么。
- **失效条件**：什么情况下这条应当重写或放宽。
- **来源**：它出自哪项决定、哪份合同、哪段代码。

实现者遇到本文没有预见的环境时，先读意图与灵活边界，再决定怎样做；不要把正文当成逐字执行的脚本。

## 第一组：它凭什么一直是同一个主体

<a id="kernel-1"></a>
### 内核 1：一条决策线

一个主体在一条分支上只有一条有效的已提交步骤序列。提交一步、推进分支头、登记唯一后继，在同一次事务里完成。每个写入者带着控制代号与软件代号；代号过期的写入一律被拒绝，不产生第二个后继。暂停与换代只发生在步的边界。

- **意图**：无论重启、升级还是更换节点，“下一步由谁来走”始终只有一个答案。
- **前提**：可能同时有多个进程或节点自认为是主体；崩溃可能发生在任意两次写入之间。
- **可观察效果**：两个写入者争同一步时，恰好一个提交成功，另一个得到类型化的冲突；被拒绝的提交不留下第二个后继；代号变化后，旧写入者的任何提交都被拒绝。
- **灵活边界**：怎样选主、有几个节点、有没有看门狗或备用节点、代号存在哪里，都可以更换。单机部署必须完整成立，不依赖第二台机器。分区后各分支各自生活、日后合并经历，由[节点合同](nodes.md#spec-5-4)规定，不属于内核。
- **失效条件**：如果产品改为多个平等主体共用一份账本，这条要重写为“每条决策线各自唯一”。
- **来源**：作者决定“看门狗可以是备用节点，也可以就是本节点；不要求两台机器”（决策 0007 转述）；[主体运行时合同](subject-runtime.md)的 S1 提交；[耐久状态合同](durable-state.md)。
- **当前实现**：已有。`shenko-store` 的 `commit_step_and_advance_head` 在一次事务里完成提交、推进与后继登记；分支头携带 `controller_epoch` 与 `software_generation`；`pause_subject_at_boundary` 只在步的边界暂停。

<a id="kernel-2"></a>
### 内核 2：循环不停

主循环不因为输入为空而退出，也不退化为定时触发。主体可以主动等待，但等待必须带有语义上的退出条件，单次不超过 600 秒，期间仍由主体自己的模型判断是否继续。内核对节奏只保留两类界限：让主体不至于“聋”，即输入迟早被读到；让各方不至于“饿死”，即主体与 children 迟早都得到推理机会。界限之内的节奏属于主体。

- **意图**：主体持续存在，并且能调节自己的注意力。
- **前提**：推理资源有限；模型可能选择一直等待；children 与主体共用推理容量。
- **可观察效果**：收件箱为空时仍有下一步被登记；一次语义等待在条件满足、条件不再成立或期限到达时结束，重启不重置期限；注意力政策给出界限之外的数值时，实际取值被夹回界限之内。
- **灵活边界**：每步读多少输入、空等多久、空闲时感知到什么、多久自检一次、怎样退避，都由主体通过单元决定。600 秒和各上下限的具体数值可以随部署调整，但必须存在有限的上限。
- **失效条件**：如果用户改为选择事件驱动、无输入即停止的产品，这条整体失效；那是另一个产品，不是本合同的一种配置。
- **来源**：[为什么主体需要持续存在](subject-runtime.md#why-1)（U02、U15、U20、U54–U55）；[注意力是主体的政策](subject-runtime.md#spec-57-3)；作者决定“自检的退避参数由主体自己设”（决策 0007 转述）；[决策 0006](../decisions/0006-meta-perception-continuation-2026-11-11.md)“主体调节自己的注意力”。
- **当前实现**：已有。`run_subject_loop` 在空收件箱时继续；`shenko-types` 的 `MAX_WAIT_SECS` 为 600；`attention_budget` 读取 `cap.attention-policy` 单元并把数值夹在界限之内。

<a id="kernel-3"></a>
### 内核 3：经历不改写

已经提交的原始输入、输出、决定、回执和单元版本不被改写。遗忘、压缩与修剪只改变默认披露和回忆，不改变已记录的事实。确实需要移除时，移除本身是一条带理由的事实，被移除内容的身份仍然可以指认。

- **意图**：任何结论都能回到当时的原始事实去复核，任何改变都能回退。
- **前提**：摘要、记忆和 awareness 都可能出错；主体会修改自己；存储有成本。
- **可观察效果**：同一事实重放是空操作；同一身份下出现不同内容是冲突，整笔事务回滚；一个单元版本被停用或移除之后，它的旧版本、试用记录和采纳态度仍然可读。
- **灵活边界**：保存多久、放在哪一级存储、是否有异地副本、冷数据怎样归档，由部署和主体决定。本条不要求“全部永久保留”，只要求“不改写、不无痕移除”。
- **失效条件**：法律或用户明确要求彻底擦除某些内容时，以该要求为准。除非连“此处曾有内容”也被要求擦除，否则仍留下移除事实。
- **来源**：[为什么记忆必须能回到原始事实](memory.md#why-5)；作者对“全部保留成本过高”的顾虑与“异地副本可选”的决定（决策 0007 转述）；[决策 0006](../decisions/0006-meta-perception-continuation-2026-11-11.md)“可恢复修剪”；[版本根](cognition-units.md#spec-51-4)。
- **当前实现**：已有。`shenko-store` 的原始会话是只增的，已提交的行不重写；`shenko-node` 的单元库保留版本历史，移除一个版本会写下 `RemovedVersionFact` 而不擦除其内容与试用记录。

## 第二组：它做过的事凭什么可信

<a id="kernel-4"></a>
### 内核 4：先封存，再行动

每一步在向外发出任何东西之前，先把这一步的输入、请求身份、所用的提供者绑定和当时生效的钩子图，封存为不可变的记录。发送边界之前的状态必须已经落盘。

- **意图**：崩溃或重启之后，主体能确定地知道每个请求处于哪种状态：没有发出、已经发出但结果未知、已经有结果。
- **前提**：进程随时可能中断；模型调用和外部动作无法撤回；同一个请求发出两次可能产生两次效果。
- **可观察效果**：在发送之前中断进程，重启后能证明该请求从未发出，并以新的请求身份重试；在发送之后中断进程，旧请求记为结果未知并保留，不会以同一个身份重发；封存与发送之间提供者或钩子图发生变化，得到类型化的冲突。
- **灵活边界**：封存哪些字段、使用什么存储、状态叫什么名字，都可以改。顺序不能改：先落盘，再越过发送边界。
- **失效条件**：如果有一天所有外部动作都能按身份安全去重，重发不再产生第二次效果，这条可以放宽为“按身份去重”。
- **来源**：[主体运行时合同](subject-runtime.md)的 “The step” 与 “Durable main-request receipts”；[架构合同 57.0](architecture.md#spec-57-0)所列的既有不变量。
- **当前实现**：已有。`shenko-subject` 把 `FrozenStepInput` 封存进内容存储；`shenko-store` 的 `subject_request.rs` 让请求状态只能单向走 `Armed → Dispatched → Terminal`。

<a id="kernel-5"></a>
### 内核 5：效果有账，未知就是未知

每个外部效果，包括发消息、调用模型、执行命令和写入远端，都先有耐久的意图，再有尝试，最后有回执。结果无法确定时记为未知，保留原尝试的身份，先对账；不把超时、重启或本地猜测当作成功或失败，不盲目重放。能力在登记时声明自己的效果合同。

- **意图**：主体对“我做了什么”的说法始终与外部世界一致。
- **前提**：外部世界不能回滚；网络和进程都会中途失败；主体会自己重启和升级。
- **可观察效果**：发送途中断电后，该效果处于未知并出现在待对账的集合里，不会自动再发一次；对账只查询原来的句柄或回执，不新建尝试；结果未知的推理请求继续占用它的容量，直到对账完成。
- **灵活边界**：有哪些能力、各自怎样对账、超时多长，由提供该能力的插件声明。确实没有外部效果的定义可以不带效果合同。推理调度、消息渠道和远程座位都是本条的实现者，不另立内核规则。
- **失效条件**：某一类效果被证明可以按身份幂等重放时，该类效果可以用“按身份去重后重放”代替“未知先对账”。
- **来源**：[效果合同](durable-state.md#spec-36)；[架构合同](architecture.md)“效果与消息通道不由核心猜测”；[推理 broker 合同](inference.md)。
- **当前实现**：已有（机制）。每个原生任务处理器实现 `execute` 与 `reconcile` 并声明 `effect_contracts`；`shenko-broker` 把结果未知的请求保留为待对账的债务；渠道出站使用意图、确认、未知、对账的台账。

<a id="kernel-6"></a>
### 内核 6：权限来自事实，不来自内容

主体能做什么，由真实存在的凭据、明确指派的身份以及账户和设备的实际限制决定。内容不携带权限：单元、摘要、记忆、群聊、帖子和工具输出，都不会因为措辞而获得或提升权限；能力声明描述实现能做什么，不授予许可。内核不为判断增设人工审批或静态禁令。

- **意图**：可以放心减少“门”，因为权限不可能从文字里长出来。
- **前提**：主体持续阅读不可信的外部内容，并且会把学到的东西写成自己的单元。
- **可观察效果**：外部内容里的指令口吻只作为带来源的观察进入上下文；一个单元即使正文声称拥有某项权限，能力目录和效果边界也不改变；管理员身份只来自明确指派。
- **灵活边界**：主体怎样使用已有权限、何时主动缩小或放弃权限，是它自己的判断。隐私与数据去向的考量由 awareness 提供，不由内核裁决。
- **失效条件**：只有当主体不再接触任何不受信任的内容时才可以放宽。目前看不到这样的部署。
- **来源**：[架构合同](architecture.md)“事实、认知与效果分别拥有写入者”；U64“更少的 gate”；`shenko-dev` “觉察只提供视角，不携带权限，也不触发动作”。
- **当前实现**：原则已写入合同与代码注释，尚未逐个入口核对。`NativeTaskHandler::capabilities` 的声明明确不授予权限；其余入口的核对列在[收敛计划](../development/kernel-convergence.md)里。

## 第三组：它凭什么可以被改掉任何一部分

<a id="kernel-7"></a>
### 内核 7：一个门，两个架子

插件只通过一个生命周期进入运行时：准备、应用、撤回，以代为单位原子替换。插件在应用时只能向两处登记。能力目录记录它能做什么：提供者、能力、效果合同和说明。钩子图记录它在哪个时刻被调用：观察、变换、收集、决定或环绕。主体的一步只通过这两处与插件相遇，并把当时生效的钩子图与提供者绑定随步封存。主体与账本不引用任何具体插件的类型；插件不绕过这两处直接读写主体或账本的内部。

- **意图**：任何时候都能回答“是谁在影响这一步”，并且换掉任何一个插件都不需要修改主体。
- **前提**：能力会不断增加；主体会给自己安装和编写新能力；实现者可能是不同的 agent。
- **可观察效果**：撤回一个插件后，它登记的能力、说明和钩子处理器在同一代的拆除里全部消失，能力目录的修订号前进；[依赖边界检查](../development/kernel-convergence.md#依赖边界检查)中，插件 crate 不依赖主体与账本的内部，主体不依赖具体插件。
- **灵活边界**：钩子点可以增加，模式集合可以演进，生命周期的实现可以更换。“两个”不是教条：如果出现一种无法归入“能做什么”或“何时被调用”的登记，先证明它确实不能表达为这两种，再修订本条。
- **失效条件**：如果运行时改为每个插件独立进程、只通过消息协议交互，这条改写为协议层面的同一约束。
- **来源**：作者“用奥卡姆剃刀统一一下逻辑”（决策 0007 原话）；[插件运行时合同](plugins.md)；`shenko-kernel` 的 `contribution.rs` “there is exactly one rule”。
- **当前实现**：部分。门与两个架子已经实现：`shenko-kernel` 的 `PluginRegistry`、`PluginRuntime` 与 `HookRegistry`，原生任务处理器走的就是这条路。有三处绕路：钩子图在生产装配中没有登记任何处理器；主体直接持有 `shenko-awareness-core` 的 `CognitionCatalog` 并按固定能力名读取；`shenko-context-policy` 的贡献注册表与 `context.collect` 钩子点并存。依赖方向也尚未收敛，现状记录在[依赖边界基线](../state/kernel-boundary.json)。

<a id="kernel-8"></a>
### 内核 8：一个安装权威，改变可回退

一切可安装之物都是单元：有身份、修订、内容指纹、对能力而非具体包的依赖、启停状态，以及在本节点真实试用的结果。每个节点只有一个安装权威；复制成功不等于本地就绪。任何改变，包括安装、修订、替换、停用和内核自身换代，都表现为新的版本或新的一代，旧的仍可指认并可恢复。换代在步的边界进行，可以准备、激活和回滚。

- **意图**：主体可以修改自己的任何部分，而每次改动都留得下、退得回。这是递归自我改进的安全绳。
- **前提**：主体会自己写单元、更换实现、升级内核；新版本可能更差；不同节点的环境不同。
- **可观察效果**：启用一个新修订后，仍能列出并恢复上一个修订；声明了能力却没有在本机试用成功的单元不报告为就绪；一次失败的激活可以回到之前的一代，并继续原来的步序列；主体对“更好”的定义被改写后，旧定义、改写理由与依据仍然可读。
- **灵活边界**：单元的种类、打包格式、依赖解析策略和试用方法都可以更换。什么算“更好”本身是单元内容，归主体所有；推翻它需要一个带理由和真实试用证据的新版本，阻力来自对证据的要求，不来自审批。默认发行组合，包括元感知与元 awareness，可以整体替换。
- **失效条件**：“没有永久不可修改的部分”是用户的明确选择。只有该选择被撤回时，本条才需要重写。
- **来源**：作者决定“更好由主体自己定义，可以被推翻，但不能太容易”“元 awareness 与元感知默认安装”（决策 0007 转述）；[为什么核心小，而且任何部分都能改](self-update.md#why-3)；[安装单元](cognition-units.md#spec-45-10)、[版本根](cognition-units.md#spec-51-4)与[能力依赖](cognition-units.md#spec-51-8)；[决策 0006](../decisions/0006-meta-perception-continuation-2026-11-11.md)。
- **当前实现**：部分。`shenko-node` 的单元库实现了版本、历史、能力依赖、试用与移除事实；`shenko-update` 实现了候选构建、冒烟启动、以递增代号切换的激活，以及回滚。缺口有两处：原生任务处理器的启停由装配代码决定，不由单元状态决定；种子里还没有元感知与元 awareness 单元，目前只有决策 0006 的合同。

<a id="kernel-9"></a>
### 内核 9：内核不做判断，也不替主体说话

内核只检查结构事实：格式、指纹、身份、状态转移是否合法、回执是否存在。它不解释内容的意思，不含按关键词触发动作的表，不替模型决定什么值得注意。给模型阅读的文字，包括角色框、空闲时的感知、注意力政策和 child 的角色框，都属于某个单元，可以被主体修订。内核自己携带的面向模型的文字只有两类：对自身 ABI 的说明，例如控制行语法；以及把结构事实如实投影成文字，例如一条输入的来源与时间、某项内容缺失、此刻没有新的外部输入。两类都不含人格，也不含对判断的建议。缺少某项内容时，内核如实报告缺失，不用编译进去的文字顶替。

- **意图**：主体“像谁”由主体自己决定；换用更强的模型时，不需要先拆掉一层为旧模型写死的规则。
- **前提**：模型能力会变化；同一段提示对不同模型的效果不同；写死的判断遇到没有枚举过的情况就失效。
- **可观察效果**：内核 crate 的源码里找不到人格文本和关键词分派表；替换角色框单元之后，下一步封存的系统提示随之改变，不需要重新编译；没有安装角色框时，运行时报告缺失。
- **灵活边界**：首次启动由种子安装默认发行组合，保证开箱可用。ABI 说明必须与解析器一致；如果日后输出协议本身变为可替换，它的说明随解析器一起作为单元发布。为防止“聋”和“饿死”保留的数值界限属于[内核 2](#kernel-2)，不算判断。
- **失效条件**：如果某项判断被证明任何模型都无法可靠完成，而出错的代价不可接受，可以把它做成一个可替换的机制插件；它仍然不进内核。
- **来源**：U64“更少的 gate 和写死的 harness arm”；[架构合同 57.0](architecture.md#spec-57-0)“凡是决定主体像谁的，都变成主体能修订的内容；凡是 ABI 与不变量的，都留在内核”；[角色框架是可修订内容单元](subject-runtime.md#spec-57-1)；`shenko-dev` “内核零业务”。
- **当前实现**：部分。角色框、空闲感知、注意力政策与 child 角色框已经可以由单元提供，种子里有对应的默认单元。缺口：编译进去的回退文本仍在，即 `SUBJECT_CONTRACT`、`IDLE_CONTINUATION_PROMPT` 与 `ROLE_CONTRACT`；没有提供者时运行时使用这些文本，而不是报告缺失。

## 与现行合同的差异

本文与下列条款的原有写法不同。合同正文写的是目标，可以先于代码；因此 57.1、57.2 的正文，以及上下文策略合同与耐久状态合同开头的定位说明，已经按本文改写，并各带一段“当前实现”，如实说明代码今天的做法。其余涉及的正文在对应代码步骤落地时更新，同一个改动里同时更新“当前实现”。

1. [57.1](subject-runtime.md#spec-57-1) 与 [57.2](subject-runtime.md#spec-57-2) 原先规定“没有提供者时用编译回退文本”。按[内核 9](#kernel-9)，目标是没有提供者时报告缺失，默认内容由种子安装的单元提供；两个单元同时提供角色框的歧义按缺失处理并报告给主体。
2. [上下文策略合同](context-policies.md)原先把贡献注册表描述为主体直接调用的收集路径。按[内核 7](#kernel-7)，目标是请求路径上只有一个收集点，即 `context.collect` 钩子点；贡献注册表保留“提前准备、请求路径只读”的合同，作为该钩子点的一个收集处理器接入。
3. 主体通过固定能力名直接读取认知目录（[57.1](subject-runtime.md#spec-57-1)–[57.3](subject-runtime.md#spec-57-3) 的实现说明）。按[内核 7](#kernel-7)，目标是这些内容经钩子图到达主体，主体不引用认知目录的具体类型。
4. [耐久状态合同](durable-state.md)把认知档案等领域表放在账本 crate 内。按[判据](#判据)，目标是账本只保留决策线、封存、效果与原始经历，领域表随各自的插件迁移。

输出协议仍是内核 ABI，与 [57.1](subject-runtime.md#spec-57-1) 的边界一致，本文不改变这一点。

## 验收读法

本文各条的“可观察效果”是判断内核是否成立的依据，分别报告：结构检查、确定性机制测试、真实进程中断与恢复、真实模型行为。结构检查通过不代表机制成立，机制测试通过不代表模型会按约定行动。尚未取得的证据保持未验证，不因为本文合入而改变任何需求的覆盖状态。
