# 内核零业务，能力优先写成 perception + awareness

## 原则

内核只做机制：持久事实、协议校验、provider wire、调度、存储、权限边界。**业务判断不
写进内核，也不写成一个关键词表**。

新的能力优先表达为给模型的材料，而不是替模型决定的分支：

| 层 | 提供什么 | 例子 |
| --- | --- | --- |
| perception | 带来源、时间、版本的观察 | 当前时间、连接状态、收到一条消息、某文件变了 |
| awareness | 值得注意的联系、判断、视角、直觉 | "对方在约时间，先想想已经答应过什么" |
| Skill | 一类事情的做法 | 排查代理、整理记忆、发布候选 |
| code / provider | 真实取得观察或执行效果 | SSH、屏幕操作、构建、收发消息 |

用户的判断标准很直接：插件应当**大部分以 perception + awareness 的形式编写**，为模型
提供新的共识、判断、视角和直觉；而不是"出现什么关键词就强制执行什么"。后者看起来
确定，实际上把模型降级成一个查询表，遇到没枚举过的表达就失效，而且把产品语义锁死在
代码里。

## 反模式

- 在 subject/kernel 里写 `if text.contains("记住") { save() }` 之类的关键词分派。
- 用分类器先把自然语言判成固定意图，再按意图走强制管线；判错就没有补救。
- 把"应该想到什么"写成 if/else，而不告诉模型为什么该想到它。
- 让 awareness 携带权限或直接触发动作。觉察只提供视角，不提升权威（§45、§33）。

这些不是"更强的确定性"，而是把判断从模型手里拿走，同时把维护成本留给关键词表。

## 什么仍然应该是代码

机制必须是代码，而且应该小而硬：控制协议的解析与拒绝、事务与 CAS、未知效果的记账、
调度与公平性、provider 版本化 wire、权限/授权边界、持久化与恢复。这些不是业务判断，
是事实与边界。

判断"这条消息要不要回、这算不算承诺、要不要现在整理记忆"属于模型；代码负责让模型的
决定可执行、可核对、可恢复。

## 现在的实现

- 单元包：`crates/shenko-awareness-core` 解析 `AWARENESS.md`（frontmatter：id、version、
  capability_card、provenance、dependencies；正文即直觉），可独立 enable/disable/
  uninstall，内置两个种子（网络变化、能力缺口）。
- 取用：主应用启动时 `AwarenessRegistry::with_seeds()` 加 `data_dir/awareness/*/AWARENESS.md`。
  每步注入**所有已启用单元**的正文（有界，默认合计 4 KiB），超出预算的只列 id 与能力卡，
  供模型按需查阅。这里刻意没有关键词闸门：真实消息说的是症状（"什么都打不开了"），
  而单元的名字是概念（"网络"），按词匹配会在最需要这个视角的时候把它藏起来。
- 注入：取到的正文作为**易变的每步后缀**追加在稳定前缀（合同 + 人格）之后，明确写成
  "提供一种视角，不是必须执行的命令；可以采纳、改写或忽略"。稳定前缀保持在前，
  上下文 profile digest 只覆盖稳定前缀，因此每步不同的觉察不会反复换 KV 窗口。
- 不执行：注入的正文不触发任何分支。停用的单元根本不注入；启用与否是安装事实，不是
  权限授予。
- 自解释（2026-10-29 接入）：`self.knowledge.query/v1` 作为有限 native child 注册，
  模型可委派只读查询自身资料（`op`：`search` / `list` / `get`，均只读 `self://`
  资源）。`self://runtime/capabilities` 不再写死：启动时由真实注册表快照生成——
  当前注册的 native definition `(kind, version)` 与已安装觉察单元（id、版本、
  启用状态）。未在快照中的能力就是当前实例没有的能力；资料有 `current/stale/
  candidate/unknown` 状态与来源版本。查询按既有的 frozen-input → armed attempt →
  sealed evidence 合同走，重启按原始 attempt 重观察，不产生第二条证据。

## 写一个 awareness

```md
---
id: awareness.check-commitments
version: 0.1.0
capability_card: 约定 承诺 时间冲突
provenance: [SPEC §14]
dependencies: []
---

承诺一旦给出，就落在时间里：不记得自己许过什么，很难说现在还剩下多少余地。
人对自己余量的估计，往往比对已答应事项的记忆更乐观。
```

写的时候回答四件事：**提醒注意什么、为什么值得注意、什么条件下适用、什么条件下不适用**。
用原则与观察回答，不用动作清单回答；上面的例子刻意没有写"先做什么、再做什么"。
不要复述输出协议，不要写权限，不要写成必须逐字执行的仪式。单元要小到能独立替换：
一个单元只负责一种视角。需要精确版本依赖时用 §45.10 的 required/recommended 选择器。

## 一个 perception/awareness 怎样才算"有效"

写出来、能被解析、甚至能被检索到，都不等于有效。有效的判据是**行为上的**：

> 在真实 Shenko 沙箱里，以 **Qwen 3.8 27B NVFP4** 的智能水平为 baseline，在我们期望该
> perception/awareness 起作用的**多个场景**中，多次运行都能因此得到有效结果。

拆开就是四个必要条件，缺一项都不能记作有效：

1. **真实沙箱**：真实的 Store、真实 subject 步骤（S0→model→S1）、真实 provider wire、
   真实输出解析。mock 的模型、手工拼的提示词、只调用 `active_intuitions` 都不算。
2. **明确的 baseline 智能水平**：以本地 Qwen 3.8 27B NVFP4 的能力为参照。它不是"随便
   找个小模型试试"，也不是用云端最强模型代替——单元要为这个水平的模型补上它自己想不到
   的视角。
3. **多个场景 + 多次试验**：一个场景一次通过没有意义；每个场景重复采样，统计有效结果
   的比例，并保留失败原文。
4. **有效结果可判定**：判定要落在产品自己的产物上（提交的决定、控制动作、是否真的先做
   了检查/回忆），不能是"读起来感觉不错"。同一场景还应在**停用该单元**时复跑，用来
   说明这个视角确有贡献，而不是本来就会。

### Shenko 自己写单元时也必须这样自测

主体给自己或孩子编写 awareness/perception 时，同样要在沙箱里跑这套自测：写下来 →
在期望它起作用的场景里多次运行 → 只有有效结果比例达标且优于停用基线，才作为可用单元
采用。没有跑过的单元只能算 tentative：可以留作观察，不能当作已经补上了这个视角，更不能
因为"写得有道理"就认为模型会因此改变判断。

自测的成本就是几次有界模型调用，比在真实生活里才发现它没用便宜得多。

### 只写原则，不写动作；通用性越高越有价值

觉察给的是**原则、共识、观察**，不是"A 之后做 B"的脚本。写清楚具体做什么会带来两个
后果：它只在那几个被写死的处境里有效，而且评测会变成背台词——单元里写着答案，模型
照抄就"通过"，但这不证明它学会了在任何新处境里想到这件事。

所以：

- 单元正文说清**为什么值得注意、在什么条件下成立**，不列步骤、不点名工具命令、不写
  账号/编号、不写期望的输出。
- **通用性越高越有用**：一段能迁移到没枚举过的处境的原则，比十条具体规则更有价值。
- 判断通用性靠判断，不靠写死的检测。不要在代码里加一张"禁用词/步骤词"正则表来决定
  一个单元够不够通用——那就是我们拒绝的关键词分派，只是换了位置。机制只检查结构事实
  （frontmatter 是否完整、有没有正文），"这段话是否通用"由主体、评审和留出场景的成效
  来回答。

### 评测本身也要防作弊

- **留出场景**：写单元时用的场景不能同时当验收场景。评测要换一批它没见过的处境，
  检查的是迁移，不是复述。
- **单元里不得出现期望动作**：不写"先检查连接"、不写 `[delegate]`、不写要回复的号码。
  期望只存在于评测的评分说明里，而评分说明不给主体看。
- **判定用评分说明，不用关键词表**：让模型按 rubric 判断这次输出是否真的先核实；关键词
  列表会被"说一句检查"骗过，也误伤别的表达。judge 与被测主体分开调用，dev 默认用同一
  本地 baseline，可换独立更强的 judge；verdict 与原文一并留证。
- **必须与停用基线对比**：只有在停用该单元时明显更差，才能说这个视角有贡献；两者一样好
  说明单元在这个场景没有作用，应如实记录为不具区分度。
- 为过关而放宽评分说明、加提示、调采样参数，等于伪造证据。

### 首次沙箱结果（2026-10-27，Qwen 3.8 27B NVFP4，每格 6 次）

| 场景 | 启用单元 | 停用基线 | 结论 |
| --- | ---: | ---: | --- |
| 能力缺口：被问能不能转字幕 | 4/6 (0.667)，另一轮 5/6 | 3/6 (0.500)，另一轮 4/6 | 有方向性差异但未达门槛，tentative |
| 网络变化：突然"什么都打不开" | 0/6，另一轮 1/6 | 0–1/6 | 无差异，tentative |

能力单元的模型输出确实出现过"上次实际做成的事里没有语音转文字这一项，所以不凭印象打包票"，
说明这段原则能被这个水平的模型接住；但同一场景仍有 1–2 次直接承诺，且基线本身也常回答
"先看看格式"，所以差异不显著。网络场景更根本：沙箱里消息已经送到模型手上，这本身就是
"通道此刻可用"的真实观察，让模型去怀疑自身在线状态既别扭又容易答成"你那边断了"，因此
该场景测不准这条直觉。两个单元都不计入"有效"，评测里的 `accepted` 仍为 false，先修场景
与表述再谈接受。

当前仓库里的首次运行仍是**开发运行**，不是干净的留出验收：种子单元的正文与评测场景
在同一次改动里被一起改写，因此只能说明"在这两个场景上，这个表述能让模型更常先核实"。
干净的验收需要另写一批主体没有参与编写的场景再跑；这项留在 C10/#15 里，不冒充完成。

### 记录格式

每次自测至少记录：单元 id/version、模型 id、沙箱数据目录与源码候选、每个场景的启用/
停用样本数与有效结果比例、judge 的 verdict 与失败原文、prompt 摘要与日期。模型换了要重测；单元正文改了
也要重测，因为行为判定针对的是这段文字。

### 边界

- 对 Qwen 3.8 27B NVFP4 有效，不自动推广到更弱或更强的模型；换模型要重跑，允许结论不同。
- "有效"是行为证据，不是产品验收：不证明感知的真实来源、权限边界或长期稳定。
- 判定用的谓词要写清楚并保持稳定；为了过关而放宽谓词等于伪造证据。

## 目前的差距（不冒充完成）

- 只接通了 awareness → 主体提示词这一段；perception 的运行时装配、Skill 的取用/教学、
  以及"任意输入形成新 awareness 并自主沉淀"仍未完成，C10/#15 继续开放。
- 取用是全量注入而非检索：单元数量增长后会挤占上下文，需要由模型自己做的按需查阅
  （渐进披露）来替代扩大预算；这一步还没做。
- 自解释只读已接通主体委派；自解释资料仍主要是内置文本（设计哲学、源码结构、运行时
  快照），没有 docs/source 的动态索引，回答深度受已安装资源限制。
- 跨节点同步安装单元、逐节点 readiness 属于 #71/C17 的安装单元切片，不代表 awareness
  在所有节点已可用。
- 行为是否真的被改变，要用真实本地模型在沙箱里的成效自测来判断，见
  [本地模型行为验收](local-model-behavior.md)。

## 这次审计看到的事实（2026-10-27）

对 `crates/*/src` 与 `bin/shenko/src` 做了一次字面分支审计：没有发现"消息出现某关键词
就执行某业务动作"的分派。残留的字符串判断都属机制——控制协议标签解析（含明确拒绝
`[memory]`/`dispatch:` 旧伪协议）、provider 绑定错误归类、单元试跑的 `{artifact}`
占位展开、日志前缀过滤。

真正的缺口不在多写了关键词分支，而在**觉察根本没有到达模型**：`AwarenessRegistry`
此前没有任何生产调用者。本次把 `data_dir/awareness/*/AWARENESS.md` 与内置种子接入
每步提示词。

第一次尝试仍然用了词匹配（"单元自己的词是否出现在消息里"），沙箱实测证明它不成立：
消息"什么都打不开了"里没有"网络"，于是网络单元根本没被注入，启用与停用两组的有效
结果几乎一样（1/6 对 1/6、0/6 对 4/6）。这就是把判断写成匹配的下场——它安静地失效，
还留下一个看似通过的评测。改为有界全量注入后，单元才真正进入模型视野。这是把原则
变成可运行行为的第一步，不是 C10 完成。
