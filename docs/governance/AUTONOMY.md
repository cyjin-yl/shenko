# 自主决定与工程约定

本规则服务于完整实现与少打扰人类。朋友的 Agent 以 `--dangerously-skip-permissions` 在自己的 fork 自主开发、合并、配置工具/CI 和持续交付。Why 见根 [WHY.md](../../WHY.md)，实际产品合同见 [SPEC](../../SPEC.md) §40/46。

所有开发者先完整读 [shenko-dev](../../.agents/skills/shenko-dev/SKILL.md)。禁止添加设计、阶段、测试方案、PR 或日常继续工作的人工 gate。既有真实授权内直接完成工作；原子开发 Skills 自由组合，不是必须走完的流程。

| 情况 | 默认动作 | 理由 |
| --- | --- | --- |
| 实现、类型、算法、依赖、接口、计划顺序、测试方法、UI细节 | 按规格和真实证据自行决定并验证 | 这些属于被委派的工程工作 |
| 多种合理方案 | 选最能满足目标的可验证方案；重要取舍记录 Why | 不把工程裁决转交给用户反复投票 |
| 规格部分尚未细化 | 查原话/相关合同与上游，采用可恢复默认；重要假设可查 | 未定细节不使整个任务冻结 |
| 工具或脚本不适用 | 找到目的、核对前提，换方法、修工具或补能力 | 流程为结果服务 |
| 内核、恢复器、数据格式、插件API需要breaking change | 自行建立候选/迁移/接续与真实恢复路径 | 任意部分可演进，已发生事实不能丢 |
| 上游PR尚未review | 在自己的 fork 继续开发、合并与验证，持续更新 PR | PR状态和完整目标进度不同 |
| 实质失败、review指出可复现缺陷 | 自主修复并验证相关范围 | 技术反馈是推进依据，不是要求人来替代调试 |
| reviewer误报或只提出风格偏好 | 给具体依据并收敛；真正无关项另记 | 审查应发现实际问题，不无限制造新gate |
| 缺账号本人验证、凭据、设备或真实权限 | 先完成可做准备；只请求最小缺失因素，其他工作继续 | 文档不能生成现实中不存在的访问能力 |
| 产品目标互相冲突，现有原话和证据无法裁决 | 展示具体冲突、已完成部分与可选影响，再问一件最关键的事 | 只有这里需要用户作新的产品选择 |

## 自动审查如何使用

普通改动采用足够的检查；跨模块、恢复性、调度、外部效果和关键体验变化引入独立验证。Reviewer 读取真实 BASE…HEAD、相关合同与原始证据；每个阻断项给位置、触发条件和影响。不能只看摘要就批准，也不能为显得严格创造规格未要求的程序。

验证投入遵循 [verify 原子](../../.agents/skills/shenko-dev-verify/SKILL.md)：优先复用已有证据，低影响小改可零新增测试；同一连贯增量禁止新增十个或更多测试，不用参数表、多个 worker 或拆 PR 规避。已有测试按影响范围运行，完整产品验收义务不等于每个小改都新增全套测试。剩余具体问题解决后即继续实现和交付。

整合者对有据的意见修复或解释；作者不直接篡改 reviewer 的原始结论。允许补充新证据、修正错误测试和改进评审方法，保留旧结果与理由。充分验证后继续交付；不要求多找几个 reviewer 才安心，也不以多数投票消除一次可复现的数据丢失。

## 完整度的收敛

定期从需求端检查已标完成的功能：实际用户能否完成旅程？错误/恢复是否真实？是否只有 UI、trait 或 stub？发现遗漏形成有来源的新任务，补齐完整用户要求。现行 147 项 R 和 216 条 case 是可查基线，无编号的正式义务也应补到验收中；已有场景和证据优先复用。

## 流程的分寸

普通工程决定由 Agent 直接推进；只在重要取舍处记录 Why，以实际风险选择足够的检查，充分验证后继续下一项。计划、脚本、harness、规则与实现都可以演进。真实缺失的外部条件精确记录；普通开发不需要等待人类接手决定。
